# flask-play

A facilities management (CAFM-style) SaaS app, pre-production. It tracks locations (sites, buildings, floors... nested to any depth), assets, jobs (reactive work), planned job schedules (planned/recurring maintenance) and suppliers.

**Current priority: build out features first. Design and UI polish come later.** Don't restyle or refactor templates unless asked. See "Deferred: design" below.

## Stack

- Flask 3, Flask-SQLAlchemy, Flask-Migrate (Alembic), Flask-WTF (CSRF is on globally), `email-validator` (for WTForms `Email()`), `resend` (email), `reportlab` (PDF downloads), `boto3` (file storage in DigitalOcean Spaces), `openpyxl` and `defusedxml` (every spreadsheet: import files, templates and downloads, see `services/spreadsheets.py`; openpyxl parses through defusedxml when it's installed, so keep both. `lxml` isn't needed: it made writing slower when measured on 2026-11-04), `tzdata` (UK time zone on Windows), `psycopg[binary]` (SQLAlchemy 2.1 uses psycopg 3 for `postgresql://` URLs) and `gunicorn` (production). They're pinned in `requirements.txt` (direct dependencies only); add new packages there.
- PostgreSQL. Primary keys are UUIDs (`sqlalchemy.dialects.postgresql.UUID(as_uuid=True)`)
- Server-rendered Jinja templates with Bootstrap 5.3 and Bootstrap Icons 1.11.3 (`<i class="bi bi-...">`) from the CDN with SRI hashes, Tom Select 2.4.3 (CDN, SRI, `tom-select.bootstrap5` theme) for searchable selects, plus a small `app/static/js/app.js` (toast auto-hide, Tom Select setup, the person form's group toggle, location narrowing, table Columns menus)
- Windows dev machine, venv at `venv/`, run with `venv/Scripts/python.exe`
- Git repo, `main` pushed to https://github.com/wh80/myfmhub-app. `.gitignore` excludes `.env`, `venv/`, `__pycache__/` and local `*.db` files. Never commit `.env` or secrets.

## Running

```
venv/Scripts/python.exe run.py               # dev server (debug)
flask db migrate / flask db upgrade          # migrations
venv/Scripts/python.exe seeder.py            # add 50 of each record type
venv/Scripts/python.exe seeder.py --clear    # wipe data first; --count N to change amount
flask make-platform-admin <email>            # grant /admin access, creating the user if new (--remove to take it away)
flask create-jobs-for-planned-job-schedules          # raise jobs from due planned job schedules (run daily by cron)
flask start-scheduled-jobs                           # move jobs whose scheduled date has arrived to In Progress (run daily by cron)
```

Config comes from `.env` via `config.py` (all of these are loaded into `Config`): `DATABASE_URL`, `SECRET_KEY`, `OTP_PEPPER`, `DO_SPACES_ENDPOINT`/`KEY`/`SECRET`/`BUCKET`, `LOCAL_FILE_FOLDER` (default `instance/documents`, gitignored; used when no bucket is set), `RESEND_API_KEY`, `EMAIL_FROM`, `APP_URL` (default `http://localhost:5000`: the site's address for links in emails sent by cron commands, which have no request; no command sends email since the start reminders were removed on 2026-11-02, but keep it for when one does), `SUPPORT_EMAIL` (default support@myfmhub.com: shown to customers, and where new support ticket notifications go). `MAX_CONTENT_LENGTH` is 25 MB for every request (a 413 redirects back with a message); uploads are limited to 20 MB and imports to 5 MB on top of that. Never hard-code secrets in `config.py`. `SECRET_KEY` and `OTP_PEPPER` are read with `os.environ[...]` and have no fallback, so the app won't start without them; keep it that way.

In local dev, `RESEND_API_KEY` is commented out in `.env`, so sign-in emails, codes included, are printed to the dev server console. That's how you sign in as seeded `@example.com` users. Uncomment it to send real email.

## Data model (`app/models.py`)

- Multi-tenant. `Organisation` is the tenant: `name`, optional `address` and `telephone` (edited on My Organisation), `suspended_at` (set by a platform admin so nobody can sign in to it), `verified_at` (see registration), and `terms_accepted_at` / `terms_accepted_by_name` / `terms_accepted_by_email` (the registrant's name and email at the time, copied rather than a foreign key to their person, so the record survives the person being deleted; see No circular foreign keys), set by registration and by the seeder (its admin). Every other model except `User`, `OTP` and `UserSession` (the login side, which spans organisations) has a non-null `organisation_id`, and `Organisation` has a `cascade='delete'` relationship to each. Link tables carry no organisation.
- **Users and people** (decided October 2026): `User` is the login, one per email across every organisation. `Person` is someone in one organisation, and their membership of it. One user can have a person in several organisations (`user.people`), for example a contractor who works for two customers, and each organisation controls its own person's name, user group and `can_login`. The app never edits a user from inside an organisation, so one organisation can't affect someone's access to another.
- `User`:
  - unique `email`. The unique constraint is case-sensitive, so lowercase emails before saving or looking them up. There's no password: login is passwordless (OTP).
  - `email_verified_at`, set by the first successful OTP
  - `is_platform_admin`: MyFmHub staff access to `/admin`. It's only set with the CLI command, which creates the user if the email is new. A platform admin can have no people at all; anyone else always has at least one (deleting someone's last person deletes their user, see `services/people.py`).
  - `last_organisation_id` (ondelete SET NULL): the organisation they last worked in, pre-selected on the Select organisation page at their next sign-in.
  - `user.signin_people(otp=None)` lists the people they can sign in as, sorted by organisation name, using `person.can_sign_in()`.
- `Person`: `first_name`, `last_name`, `email`, optional `job_title` and `mobile`, plus:
  - `user_id` (required, ondelete CASCADE), with `UniqueConstraint('organisation_id', 'user_id')`: a user is in an organisation at most once.
  - `can_login` (default False): the organisation's choice. Registration sets it to True.
  - `user_group_id` (ondelete RESTRICT): their permission group in this organisation, see `UserGroup`. Only required when `can_login` is on (`PersonForm.validate_user_group_id`). `person.is_org_admin` is True when it's the Admin group.
  - `person.can_sign_in(otp=None)`: `can_login`, the organisation isn't suspended, and it's verified (or `otp` is the code sent when this person registered it).
  - `Person.email` always equals `person.user.email`. Changing a person's email moves them to the user with that email (`change_person_email()`), never edits the shared user.
- `UserGroup` belongs to an `Organisation` (`organisation.user_groups`, cascade delete) and has `people`. It stores `name` (unique per organisation) and `is_admin`.
  - `UserGroupPermission` rows (`user_group_id` and `permission`, composite PK, no id or timestamps, like a link table) are the permissions it's granted. `user_group.permission_keys` returns them as a set.
  - Registration calls `create_default_groups(org)`, which makes Admin (`is_admin`, full access, can't be renamed, changed or deleted) and Team (every grid permission). The registrant goes in Admin. The seeder does the same: first person Admin, the rest Team.
- `OTP` belongs to a `User` (ondelete CASCADE, `user.otps`). `person_id` (ondelete SET NULL) is set on codes sent for one organisation (registration and invites): signing in with that code goes there, and a registration code is what verifies a new organisation. It stores `code_hash`, an HMAC-SHA256 of the 6-digit code peppered with `OTP_PEPPER`, never the code itself. It also has `expires_at` and `used_at` (both `DateTime(timezone=True)`, unlike the naive `created_at`/`updated_at`; SQLite returns them naive) and `attempts`.
- `UserSession` belongs to a `User` (ondelete CASCADE, `user.sessions`). It stores:
  - `person_id` (ondelete SET NULL): the organisation the session is working in, as the user's person there. Everything organisation-scoped goes through it (`g.person`). NULL while a user with several organisations chooses one, or for a platform admin outside any organisation.
  - `token_hash`: SHA-256 of the cookie token, unique
  - `expires_at`: 30 days
  - `revoked_at`: set it to log a session out
  - `last_seen_at`: written at most every 5 minutes
  - `user_agent` and `ip_address`: `request.remote_addr`. Behind a proxy or load balancer, this needs Werkzeug's `ProxyFix`. It's named `UserSession` to avoid a clash with Flask's `session` and `db.session`.
- **Addresses**: `Location`, `Supplier` and `Organisation` have one optional `address` (`String(500)`, lines separated by `\n`; it replaced six separate fields, line one to post code, on 2026-11-02). The form has a textarea and saves it through `clean_address()` (`services/addresses.py`: each line trimmed, blank lines dropped, None when empty). Overviews show it with `white-space: pre-line`. The data export has one Address column (a wrapped multi-line cell). The locations and suppliers imports have one `address` column (Column kind `address`), where commas separate the lines and are dropped, e.g. `1 High Street, Leeds, LS1 1AA`. It isn't on the index pages or downloads.
- **Locations** (replaced Site, Building and Zone on 2026-11-03 at the user's request): `Location` (`name` up to 100, optional `address`, `telephone` and `email` (blank stored as NULL, validated like a supplier's, on the form, the overview as a `mailto:` link, the data export and the locations import, not on the index or downloads), `organisation_id`, `import_event_id`) nests to any depth through `parent_id` (self-referencing, ondelete CASCADE; `location.parent`, `location.children` by name with ORM `cascade='delete'`). Deleting a location deletes every location inside it and the assets, jobs and planned job schedules at all of them (`Location.jobs`/`assets`/`planned_jobs`, cascade delete, and their `location_id` FKs are ondelete CASCADE); documents are only unlinked. Optional `main_contact_id` (a person in the organisation, ondelete SET NULL; `location.main_contact`, `person.main_contact_locations`) is a searchable select on the location form (`set_main_contact_choices()` in `routes/locations.py`, everyone in the organisation) and shows on the overview, linked with `people.view`; it's in the data export and the locations import (`main_contact`, kind `person`: a full name or `Name (email)`, with a dropdown of people in the Excel template; an email-only column was tried and dropped earlier on 2026-11-03 as unintuitive), not on the index or downloads. Optional `location_category_id` (ondelete SET NULL, `location.location_category`, reference data) says what kind of place it is (Site, Building, Floor...), since nesting is free-form; it's only on the location form, never on the asset, job or planned job schedule location selects.
  - `materialised_path` (`String(1000)`, set by the app only) is the names from the top down joined with ` > ` (`SEPARATOR` in `services/locations.py`), e.g. `Head Office > Main Building > Ground Floor`, and `str(location)` is it. It's unique per organisation: DB `UniqueConstraint('organisation_id', 'materialised_path')` plus the case-insensitive `path_taken()`, which is what stops duplicate names in the same place (`My Site > My Building` and `my site > my building` clash). Names can't contain `>`, so a path always splits back into its names. `set_path(location)` sets the path from the parent and name and recurses into the children; call it after any rename or move. `path_problem(org_id, name, parent, location=None)` returns `(field, message)` or None: a `>` in the name, a move inside itself or a descendant, a taken path, or a path (including the descendants' new paths) over `MAX_PATH_LENGTH`. Other helpers: `build_path()`, `normalise_path()` (tidies spacing around `>` for typed paths), `find_by_path()`, `descendants()`, `subtree_ids(location)` (a subquery of the location and everything inside it, by path prefix with `startswith(..., autoescape=True)`) and `location_tree()` for the index.
  - `Asset`, `Job` and `PlannedJobSchedule` have one required `location_id` (`record.location`). `raise_job()` copies it from the schedule; sub-assets and follow-up jobs start at the parent's location (changeable).
- `Job` is at a `Location`, and optionally to a `PlannedJobSchedule` (`planned_job_schedule_id`, ondelete RESTRICT). Optional `estimated_cost` and `actual_cost` (`Numeric(12, 2)` pounds, on `JobForm` with a £ prefix via `money_field()` from `_number_fields.html`) are on the edit page only, not create (the create route ignores them; since 2026-11-03), and show on the overview, the data export and the jobs import, not on tables or index downloads. The create page has a Back button to where it was opened from (`back_url`: the asset's or location's Jobs tab, the parent's Follow Up Jobs tab, or the index), which is also where saving goes.
  - `status` is a key from `JOB_STATUSES` in `app/models.py` (`new`, `unassigned`, `pending_acceptance`, `pending_scheduling`, `pending_start`, `in_progress`, `completed`, `closed`, `rejected`; default `new`, enforced by the `ck_job_status` check constraint). `job.status_label` gives the display text and `jobs/_status_badge.html` renders it as a badge. It's set by the app only, never on `JobForm`. `JOB_FINISHED_STATUSES` (`closed`, `rejected`) are the ones a job doesn't move on from: `overdue_conditions()`, the dashboard's Compliance Risks and the index's `not_closed` filter ("All Open Jobs") leave them out. `ASSIGNED_JOB_STATUSES` (those from `pending_acceptance` to `completed`; `job.has_assignee_status` in templates) are the ones with an assignee, where Add Helpers works. Reassign works on the same statuses except `completed` (`job.can_reassign`). **The workflow (simplified 2026-11-02 at the user's request, after testing a version with a separate `Assignment` per assignee, each accepting, starting and completing independently, with emailed token links; that was dropped as too complex):** New → Approve (to Unassigned) or Reject → Assign (one supplier or one person, plus helpers) → the steps below → Complete → Close. **Assigned and Started aren't statuses** (decided 2026-11-05 at the user's request): on many jobs they meant the same thing, so a job with its assignee is either waiting on a named step or `in_progress`. `set_work_status(job)` (`services/jobs.py`) is the one place that decides, called on assigning, accepting and scheduling: pending scheduling if it needs a date and has none, else pending start if it needs start confirmation or the date is in the future, else in progress. **Scheduled was merged into Pending Start on 2026-11-06 at the user's request:** both mean the work hasn't started. What moves a job on from Pending Start is the assignee pressing Start if it needs start confirmation, otherwise the date arriving, so `job.can_start` needs `require_start_confirmation` and there's deliberately no Start button without it: to begin early, reschedule to today. Everything is on the one job; there are no assignment records.
  - **Approve and reject** (extra permission `jobs.approve`, "Approve or reject new jobs"): while a job is `new`, its header shows Approve, a POST form to `/jobs/<id>/approve` (`jobs.approve`) that sets status `unassigned` and `approved_at` and goes back to the job, and Reject, a link to GET/POST `/jobs/<id>/reject` (`jobs.reject`, also needs `jobs.approve`), whose `JobRejectForm` takes a required `rejection_reason` (Text, up to 2000 characters, shown on the overview and in the data export). POST sets status `rejected`, `rejection_reason` and `rejected_at`, and redirects to `/jobs`. `approved_at` and `rejected_at` (`DateTime(timezone=True)`) show on the overview and in the data export. Both routes refuse a job that isn't new. **Approving in bulk** (added 2026-11-05): on the jobs index only, with `jobs.approve` or `jobs.assign` (each dropdown item needs its own), `{% set job_actions %}` adds a checkbox to each row and card and an Actions dropdown above the table to `job_list.html` (not the jobs tabs, which share the partial). The checkboxes join `#job-actions-form` with their `form` attribute, the header checkbox ticks the page, and `app.js` (`data-row-actions`) disables the button until something's ticked and keeps a job's desktop and mobile checkboxes the same. POST `/jobs/approve-selected` (`jobs.approve_selected`, needs `jobs.approve`) applies `approve_job()`, the same as the single route, to the ticked jobs that are new, and goes back to the same list (`next`). Jobs that aren't new are left alone and counted in one flash: success when all were approved, otherwise a warning ("3 jobs approved. 2 jobs couldn't be approved because they are not new."). Add further actions as `formaction` buttons in that dropdown. **Planned jobs can be rejected**: when `job.closes_with_schedule_update`, the reject page shows the schedule and `JobRejectForm(latest=next_due_date(uk_today(), frequency))` asks for a required `next_due_by` (pre-filled with that date; not before today or after it, the same rule as Update schedule via `validate_next_due_by_range()`), and the POST rejects the job and sets the schedule's `next_due_by` and `next_job_creation_date` in one commit. A rejected job has no Close button. A rejected job that isn't planned shows Reopen (`jobs.reopen`, the same route as for closed jobs), which sets status back to `new` and clears `rejected_at` and `rejection_reason`; a rejected planned job can't be reopened (its schedule has moved on).
  - **Assigning** (extra permission `jobs.assign`, "Assign jobs, and start and complete them for the assignee"; routes in `routes/jobs.py`): the job is given to one supplier (`assigned_supplier_id`, `job.assigned_supplier`, `supplier.assigned_jobs`) or one person (`assigned_person_id`, `job.assigned_person`, `person.assigned_jobs`), never both (`ck_job_assignee`); `job.assignee`, `job.assignee_name` and `job.is_assignee(person)`. Both FKs are ondelete RESTRICT with `passive_deletes='all'`, and the relationships need `foreign_keys` (as does `closed_by`), because job has several person FKs. **Helpers** are people in the `job_helpers` link table (both FKs CASCADE; `job.helpers` by name, `person.helping_jobs`): they aren't notified and can't start or complete. `issued_at` and `assigned_by_id` (the person who did it, ondelete SET NULL, `job.assigned_by`, `person.jobs_assigned_by`; blank on imported jobs; Assigned By on the overview, linked with `people.view`, and Assigned By and Assigned By ID in the data export) are set by Assign and Reassign in `give_job_to()`. `assigned_at` is the same time unless the job is waiting on acceptance, when it stays NULL until the assignee accepts (decided 2026-11-05 at the user's request). The pages:
    - **Assign** (header button while `unassigned`; GET/POST `/jobs/<id>/assign`, `jobs.assign`, `jobs/assign.html`; refuses any other status): `JobAssignForm` has `assignee`, one select grouped into Suppliers and People (values `supplier:<id>` / `person:<id>`; the route sets a flat `choices` list for validation from `assignee_options()`, and the template renders the optgroups itself), and an optional `helper_ids` multi-select of everyone; the lead can't also be a helper. POST sets the assignee (`give_job_to()`), the helpers and status `assigned`, commits, then `tell_assignee()`.
    - **Assigning in bulk** (added 2026-11-05; Assign in the jobs index's Actions dropdown, see Approving in bulk): POST `/jobs/assign-selected` (`jobs.assign_selected`, needs `jobs.assign`) with `job_ids` renders `jobs/assign.html` titled "Assign 5 Jobs", counting only the unassigned jobs, with a warning alert about the rest. The page posts every selected id back with `confirmed=1` (the same pattern as `documents.delete`), so statuses are checked again. It gives the jobs to one assignee and the same helpers through `assign_job()`, as the single route does, and goes back to the list with one flash, like approving (a warning when some were left out, "5 jobs assigned to Bob. 2 jobs couldn't be assigned because they are not Unassigned."). If nothing selected is unassigned, it never shows the page. `tell_assignee(jobs)` sends one notification or email per job, and rolls failures into one flash per kind. Emails go one at a time in the request (at most 25, a page's worth; Resend's limit was 10 requests a second when checked on 2026-11-05), so the form has `data-busy`.
    - **Require Acceptance** (added 2026-11-05; `require_acceptance`, on Assign, bulk assign and Reassign): `assign_job()` sets status `pending_acceptance` and leaves `assigned_at` blank (`issued_at` is `DateTime(timezone=True)`, shown on the overview and in the data export). Only the assignee responds, not helpers. Accept (`accept_job()`) moves it on with `set_work_status()` and sets `assigned_at`. Decline (`decline_job()`; **Reject was renamed Decline for assignees on 2026-11-06**, to tell it from rejecting a new job, and a reason is required) moves it to `unassigned` and clears the assignee, helpers, `assigned_at`, `assigned_by` and `issued_at`, and notifies whoever assigned it (not if they're the one rejecting it, or they can't sign in). The job's notes are the record of it, with the reason. This isn't the same as rejecting a new job (status `rejected`, `rejected_at`). A person who can sign in gets a notification whose button says Accept / Decline Job and opens GET/POST `/jobs/<id>/respond` (`jobs.respond`, `jobs/respond.html`, in `ASSIGNEE_ENDPOINTS`, so also open to anyone with `jobs.assign`, who responds for them; the job header has an Accept / Decline button). This is how a job with no way to reach the assignee (a supplier with no email) gets answered. A supplier or a person who can't sign in gets the email with a button to the public `/job-response/<token>` (`job_responses` blueprint, no login, same template). The token is itsdangerous-signed (`make_link_token()`, salt `job-link`), lasts `RESPONSE_LINK_DAYS` (30) and names the job and its `issued_at`, so answering, or reassigning (which resets `issued_at` while issued), stops old links working (`job_for_link()`, which also refuses a suspended organisation). GET changes nothing, so mail scanners can't answer, and that page must only show what the email already shows. Imports can set any of these statuses (they need an assignee; nobody is told and `issued_at` stays blank, so it's answered on the job page; Pending Start turns on `require_start_confirmation`, as an imported job has no date to wait for).
    - **Require Start Confirmation** (`require_start_confirmation`, stored on `job.require_start_confirmation`, chosen again by Reassign, cleared by rejecting): the job waits at `pending_start` until the assignee presses Start, which sets `started_at`. Without it nobody presses anything, so `started_at` stays blank: it's only ever a time someone confirmed. A supplier or a person who can't sign in gets a link for the next step, to a public page that needs no sign-in, lasting `WORK_LINK_DAYS` (365, because work can be booked months ahead). **Start Job** (`/job-response/<token>/start`, `job_responses.start`, `start_job()`) goes in the last email before the work starts: the assignment email, or the follow-up to accepting or scheduling. **Complete Job** (`/job-response/<token>/complete`, `job_responses.complete`, `jobs/complete.html` with `public`, `JobCompleteForm`, `complete_job()`) goes after Start if start confirmation is required, otherwise after scheduling or acceptance if those are required, otherwise in the assignment email. `notify_assignee()` picks the links from `job.can_schedule`, `job.can_reschedule`, `job.can_start` and `job.can_complete`, so Reassign sends the new assignee the right ones. The follow-up emails come from `tell_next_step(job, after, responder)` (`after` is `accepted`, `scheduled` or `started`), which sends nothing when the assignee did it in the app themselves; someone with `jobs.assign` doing it for them triggers a notification or email to the assignee, and a failure is logged, with a flash in the app. All the links use `make_link_token(job, step)` and `job_for_link(token, step)`, so a link only works for its own step. Nobody is told when a job is completed by link.
    - **Require Scheduling** (`require_scheduling`, stored on `job.require_scheduling`, chosen again by Reassign, cleared by rejecting with `scheduled_for`): the job goes to `pending_scheduling` at assignment, or on acceptance if that's required too, until the assignee chooses a date (`scheduled_for`, Date; `JobScheduleForm(due_by=...)`; `schedule_job()`), which shows on the overview and in the data export. Then it's `pending_start`, unless there's no start confirmation and the date is today, which goes to `in_progress` at once. `flask start-scheduled-jobs` (`start_jobs_scheduled_for_today()`, run daily, catches missed runs with `<=`) moves `pending_start` jobs without start confirmation to `in_progress` when their date arrives. `job.can_reschedule` allows changing the date until the work starts: `pending_start`, and `in_progress` only without start confirmation, because that job got there by itself; a later date puts it back to `pending_start`, and today moves it to `in_progress`. People who can sign in get a notification whose button says Schedule Job (`notification_button()`) and opens `/jobs/<id>/schedule` (`jobs.schedule`, `jobs/schedule.html`, in `ASSIGNEE_ENDPOINTS`, so also open to `jobs.assign`, which schedules for them; the job header has Schedule and Reschedule). Suppliers and people who can't sign in get a Schedule Job link to the public `/job-response/<token>/schedule` (`job_responses.schedule`, step `schedule`, `WORK_LINK_DAYS`), in the assignment email, or the follow-up to accepting. The same link reschedules. After the first date, `tell_next_step(job, 'scheduled')` sends one email with the next step's link (Start Job, or Complete Job) and a reschedule link. A change of date tells whoever assigned the job (`tell_assigner()`, not if they did it or the date's unchanged), and doesn't email the assignee. The date can't be in the past or after `due_by`, except that a `due_by` already passed doesn't apply, otherwise an overdue job (planned jobs' due dates can't be edited) could never be scheduled. Editing a job's due date doesn't check `scheduled_for`.
    - **Reassign** (header button while `job.can_reassign`, so not once completed: more work after that is a follow-up job; GET/POST `/jobs/<id>/reassign`, `jobs.reassign`, same template with `JobReassignForm`, which has the same three Require options, unticked, but no helpers): the choices leave out the current assignee. It goes through `assign_job()`, so the options set the status exactly as on Assign, even if the job was in progress (decided 2026-11-06 at the user's request, after a separate `Assignment` model was built and undone the same day: the job's status says where the job is now, and that's waiting on the new assignee). `scheduled_for` is cleared because the date was the previous assignee's, `started_at` is cleared unless the job goes straight to `in_progress`, and helpers stay (a helper made lead stops being a helper). `issued_at` resets, so the previous assignee's links stop working, and their unread notifications about the job are marked read. Then it tells the new assignee, and tells the previous one they're no longer required (`notify_previous_assignee()`, added 2026-11-06, not if you reassign it from yourself): a person who can sign in gets a notification with no job link, as they may not be able to open the job any more; anyone else gets `emails/jobs/reassigned.html`, and a missing address or failed email is flashed. If the new assignee rejects it, the job goes to Unassigned like any other rejection.
    - **Add Helpers** (a button next to Helpers on the overview, while in `ASSIGNED_JOB_STATUSES`; GET/POST `/jobs/<id>/helpers/add`, `jobs.add_helpers`, `jobs/add_helpers.html`, `JobHelpersForm`): people not helping already, less the lead. Each helper on the overview has a remove button (`bi-x-circle`, with `jobs.assign`, same statuses): a POST form to `/jobs/<id>/helpers/<person id>/remove` (`jobs.remove_helper`; 404 for someone who isn't a helper on the job). Neither adding nor removing tells anyone.
    - **Who's told** (`notify_assignee(job, assigned_by)` in `services/jobs.py`, called by `tell_assignee()` after the commit; nobody is told when you assign a job to yourself, because the job page the route redirects to would mark it read at once): a person who `can_sign_in()` gets an in-app notification ("<name> assigned you a job: <description>", see `Notification`) and no email; a supplier, or a person who can't sign in, gets `emails/jobs/assigned.html` (the job's details, no links). It returns False when there's no email address (suppliers' is optional), and the route flashes a warning; a failed email is logged and flashed. Either way the job stays assigned.

## Code layout and conventions

- Routes: one blueprint per resource in `app/routes/`: `locations`, `assets`, `jobs`, `planned_jobs` (URL `/planned-jobs`), `suppliers`, `people`, `user_groups` (URL `/user-groups`), plus `my_organisation` (URL `/my-organisation`), `documents` and `notifications` (see Notifications). All are registered in `app/__init__.py`. URLs use hyphens; endpoints and templates use underscores.
- `organisations` blueprint (`/organisations` prefix) holds `register()`, but that view is mounted at the root `/register` (`/login` is mounted the same way, see `auth` below) with `app.add_url_rule(..., endpoint='organisations.register')` in `create_app`, so `url_for('organisations.register')` gives `/register`. `terms()` (`organisations/terms.html`, a placeholder for now) is mounted the same way at the public `/terms`, and `RegisterForm.accept_terms` is a required checkbox linking to it (registration records it in `terms_accepted_at`, `terms_accepted_by_name` and `terms_accepted_by_email`). Registration creates an Organisation and an admin Person (with `can_login`) in one commit. The email is stripped and lowercased; an email that already has a user reuses it (`find_or_create_user()`), so one login can register several organisations, after a rate-limit check on that user. The organisation starts with `verified_at` NULL: anyone can type any email here, so it isn't offered at sign-in or in Switch organisation until the code sent now (`create_otp(user, person)`, which carries the person) is entered, and `choose_person()` then sets `verified_at`. It redirects to the validate page. If sending fails it still goes there, with a warning to use "Send a new code", which keeps the organisation.
- **People** (`/people`, `app/routes/people.py`):
  - Index, view, create, edit and delete like the other resources, gated by the `people.*` permissions like everything else.
  - The form has a required User Group select, built from `org_query(UserGroup)`. Non-admins don't see the Admin group in the list, can't edit, delete or resend to an admin (`require_can_manage`, 403), and can't change their own group.
  - The organisation must always have at least one admin who can log in (`other_active_admins(person)`). Edit refuses to move the last one out of Admin or turn off their login, and delete refuses to remove them.
  - After an edit, if you can no longer see people (you moved yourself to a smaller group), you're sent to the dashboard.
  - Templates: tabbed `people/view/` (Overview, and Assets: the person's `assigned_assets` through `asset_list.html`; the Assets tab and `people.assets` also need `assets.view`, so the tab is hidden and the route gives a 403 without it) and an inline table in `index.html`. The search covers first, last and full name, email and job title.
  - Create lowercases the email. `email_in_organisation()` refuses an email already used by someone in this organisation. Other organisations don't matter: an email with a user elsewhere links to that user (`find_or_create_user()`), with the same response as a new one, so the form never reveals that an email has an account.
  - Edit: changing the email calls `change_person_email()` (`services/people.py`), which moves the person to the user with the new email (creating it), ends the person's sessions here, and deletes the old user if nothing else uses it. It never edits a user's email, because the user may be in other organisations (otherwise one organisation could change Bob's email to its own address and sign in as Bob elsewhere). Changing your own email signs you out.
  - Turning `can_login` on, or changing the email of someone who can log in, calls `send_invite()`: it checks the rate limit, then `create_and_send_otp(person.user, person, invited_by=<name>)`, whose subject is "<name> added you to <organisation> on MyFmHub", and flashes the outcome. Adding someone without login sends nothing. Turning login off calls `revoke_person_sessions(person)`, which ends only the sessions working in this organisation.
  - POST `/people/<id>/send-invite` (needs `people.edit`) is the "Resend sign-in email" button on the view page. It shows when `can_login` is on and it isn't your own record, and it calls `send_invite()`.
  - Delete calls `delete_person()`: it ends the person's sessions here, deletes the person, and deletes their user only if this was their last person (and they aren't a platform admin).
  - Nobody can remove their own `can_login` or delete themselves.
- **Permissions** (`app/services/permissions.py`):
  - Keys are `<resource>.<action>`. `RESOURCES` (locations, assets, jobs, planned_jobs, suppliers, people, documents) × `ACTIONS` (view, create, edit, delete), less `NOT_GRANTABLE` (grid cells shown as n/a; empty at the moment), plus `EXTRA_PERMISSIONS` (`jobs.approve`, `jobs.assign`, `jobs.close`, `jobs.reopen`, `imports.manage`, `exports.manage`, `reference_data.manage`, listed under the grid), make up `GRANTABLE`, the grid on the user group pages.
  - `ADMIN_ONLY` (`organisation.manage`, `sessions.manage`, `user_groups.manage`) is never stored on a group: only the Admin group has these.
  - `can(person, key)`, called with `g.person`: the Admin group always passes, otherwise the key must be in the person's group's `permission_keys`. Templates use the global `can('jobs.edit')` (the signed-in user in the session's organisation) to hide buttons and navbar links.
  - `clean_permissions()` drops unknown and admin-only keys, and adds `<resource>.view` whenever create, edit or delete is given. `set_permissions(group, keys)` applies the difference.
  - **Enforcement**: every resource blueprint and `user_groups` registers `before_request(require_login)` then `before_request(require_permission)`. `require_permission` looks up `request.endpoint` in `ENDPOINT_PERMISSIONS` and gives a 403 if the group lacks the permission, or if the endpoint isn't listed. When you add a route to one of these blueprints, add its endpoint to `ENDPOINT_PERMISSIONS` or it will always 403.
  - The convention is: index, view and related tabs need view; create, edit and delete need their own; link and unlink need edit on the record you're on (for example `jobs.link_assets` needs `jobs.edit`).
  - New custom groups start with view on every resource.

    - `clear_session_cookie(response)` deletes the cookie. `as_utc()` normalises SQLite's naive datetimes for comparison.

## Testing

There's no test suite yet. Changes have been checked with throwaway scripts against SQLite, never the dev Postgres database:
- Set `DATABASE_URL=sqlite:///<scratch path>/x.db`. An environment variable overrides `.env`.
- Run `db.create_all()`, then `seeder.py`, then use `app.test_client()` with `WTF_CSRF_ENABLED = False`.
- Postgres UUID columns work on SQLite through SQLAlchemy's generic UUID fallback. One catch: SQLite rejects string IDs assigned to UUID columns (`'str' object has no attribute 'hex'`), for example a str id assigned in a create or edit route. Postgres accepts them, so treat that error as a test-setup artifact, not an app bug. To test successful form saves anyway, patch the bind processor before `create_app()`: wrap `sqlalchemy.sql.sqltypes.Uuid.bind_processor` so its processor converts a `str` with `uuid.UUID(value)` first.

## Known gaps / feature backlog

- **Large Export data**: `export_xlsx()` writes about 30,000 cells a second on the dev machine (measured 2026-11-04: 20,000 rows of 18 columns took 12 seconds; CSV was near instant), in the request, and gunicorn's default timeout is 30 seconds. An organisation with tens of thousands of jobs (about 35 columns each) could hit that. If so, build it in a thread and email a link, as Download all documents does, or raise the timeout.
- **Documents export**: the zip is built by a thread in the web server, in a temporary file, so it uses the web instance's memory, CPU and disk while it runs, and a deploy or restart part-way through fails it (the user asks again). If exports become common or very large, move it to a worker.
- **Raising jobs from schedules**: `flask create-jobs-for-planned-job-schedules` (`app/commands.py`) calls `create_scheduled_jobs()` in `services/jobs.py`. It's meant to run once a day from a DigitalOcean App Platform cron job.
  - It picks schedules with `next_job_creation_date <= uk_today()`. It uses `<=` so a missed run or a creation date already in the past is still caught. NULL never matches, so a schedule has at most one job raised and waiting at a time, and one run raises at most one job per schedule.
  - "Today" is the UK date (`Europe/London` via `zoneinfo`, which needs the `tzdata` package on Windows), never the server's UTC date, so BST doesn't shift which day a schedule falls on.
  - `raise_job()` copies description, work required, statutory compliance, location, job category, estimated cost, organisation and linked assets. It sets `due_by` from `next_due_by`, `planned_job_schedule_id`, status `new` and source `planned`. It leaves `next_due_by` unchanged and sets `next_job_creation_date` to NULL. The schedule moves on when the job is closed, through Update schedule (see `Job`), using `next_due_date()` (calendar months and years; the 31st clamps to a shorter month's end). Reopening a job or deleting its open job doesn't touch the schedule yet.
  - Each schedule is locked (`FOR UPDATE SKIP LOCKED`), rechecked and committed on its own. A failure is rolled back and logged, the rest carry on, and the command exits non-zero at the end. `JobForm` deliberately has no planned job schedule field, so don't add one.
- `Supplier` has an optional `email` (blank stored as NULL, validated by `Email()` on `SupplierForm`), on the form, the overview (as a `mailto:` link), the data export and the suppliers import (an optional `email` column, validated and lowercased like the people import's), not on the index or downloads.
- `Supplier` has tabs Overview and Documents.
- Registration, OTP validation, sessions, rate limiting, suspension and `/admin` work. Still missing:

  - record-level rules, for example engineers only seeing jobs assigned to them
