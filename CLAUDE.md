# flask-play

A facilities management (CAFM-style) SaaS app, pre-production. It tracks locations (sites, buildings, floors... nested to any depth), assets, jobs (reactive work), job schedules (planned/recurring maintenance) and suppliers.

**Current priority: build out features first. Design and UI polish come later.** Don't restyle or refactor templates unless asked. See "Deferred: design" below.

## Stack

- Flask 3, Flask-SQLAlchemy, Flask-Migrate (Alembic), Flask-WTF (CSRF is on globally), `email-validator` (for WTForms `Email()`), `resend` (email), `reportlab` (PDF downloads), `boto3` (file storage in DigitalOcean Spaces), `openpyxl` and `defusedxml` (Excel import files and templates; openpyxl parses through defusedxml when it's installed, so keep both), `tzdata` (UK time zone on Windows), `psycopg[binary]` (SQLAlchemy 2.1 uses psycopg 3 for `postgresql://` URLs) and `gunicorn` (production). They're pinned in `requirements.txt` (direct dependencies only); add new packages there.
- PostgreSQL. Primary keys are UUIDs (`sqlalchemy.dialects.postgresql.UUID(as_uuid=True)`)
- Server-rendered Jinja templates with Bootstrap 5.3 and Bootstrap Icons 1.11.3 (`<i class="bi bi-...">`) from the CDN with SRI hashes, Tom Select 2.4.3 (CDN, SRI, `tom-select.bootstrap5` theme) for searchable selects, plus a small `app/static/js/app.js` (toast auto-hide, Tom Select setup, the person form's group toggle, location narrowing, table Columns menus)
- Windows dev machine, venv at `venv/`, run with `venv/Scripts/python.exe`
- Git repo, `main` pushed to https://github.com/wh80/myfmhub-app. `.gitignore` excludes `.env`, `venv/`, `__pycache__/` and local `*.db` files. Never commit `.env` or secrets.

## Running

```
venv/Scripts/python.exe run.py               # dev server (debug)
flask db migrate / flask db upgrade          # migrations
venv/Scripts/python.exe seeder.py            # add 50 of each record type
venv/Scripts/python.exe seeder.py --clear    # wipe data first; --count N to change amount
flask make-platform-admin <email>            # grant /admin access, creating the user if new (--remove to take it away)
flask create-jobs-for-job-schedules          # raise jobs from due job schedules (run daily by cron)
```

Config comes from `.env` via `config.py` (all of these are loaded into `Config`): `DATABASE_URL`, `SECRET_KEY`, `OTP_PEPPER`, `DO_SPACES_ENDPOINT`/`KEY`/`SECRET`/`BUCKET`, `LOCAL_FILE_FOLDER` (default `instance/files`, gitignored; used when no bucket is set), `RESEND_API_KEY`, `EMAIL_FROM`, `APP_URL` (default `http://localhost:5000`: the site's address for links in emails sent by cron commands, which have no request; no command sends email since the start reminders were removed on 2026-11-02, but keep it for when one does), `SUPPORT_EMAIL` (default support@myfmhub.com: shown to customers, and where new support ticket notifications go). `MAX_CONTENT_LENGTH` is 25 MB for every request (a 413 redirects back with a message); uploads are limited to 20 MB and imports to 5 MB on top of that. Never hard-code secrets in `config.py`. `SECRET_KEY` and `OTP_PEPPER` are read with `os.environ[...]` and have no fallback, so the app won't start without them; keep it that way.

In local dev, `RESEND_API_KEY` is commented out in `.env`, so sign-in emails, codes included, are printed to the dev server console. That's how you sign in as seeded `@example.com` users. Uncomment it to send real email.

## Data model (`app/models.py`)

- Multi-tenant. `Organisation` is the tenant: `name`, optional `address` and `telephone` (edited on My Organisation), `suspended_at` (set by a platform admin so nobody can sign in to it), `verified_at` (see registration), and `terms_accepted_at` / `terms_accepted_by_name` / `terms_accepted_by_email` (the registrant's name and email at the time, copied rather than a foreign key to their person, so the record survives the person being deleted; see No circular foreign keys), set by registration and by the seeder (its admin). Every other model except `User`, `OTP` and `UserSession` (the login side, which spans organisations) has a non-null `organisation_id`, and `Organisation` has a `cascade='delete'` relationship to each. Link tables carry no organisation.
- **Users and people** (decided October 2026): `User` is the login, one per email across every organisation. `Person` is someone in one organisation, and their membership of it. One user can have a person in several organisations (`user.people`), for example a contractor who works for two customers, and each organisation controls its own person's name, user group and `can_login`. The app never edits a user from inside an organisation, so one organisation can't affect someone's access to another.
- `User`:
  - unique `email`. The unique constraint is case-sensitive, so lowercase emails before saving or looking them up. There's no password: login is passwordless (OTP).
  - `email_verified_at`, set by the first successful OTP
  - `is_platform_admin`: MyFmHub staff access to `/admin`. It's only set with the CLI command, which creates the user if the email is new. A platform admin can have no people at all; anyone else always has at least one (deleting someone's last person deletes their user, see `services/people.py`).
  - `last_organisation_id` (ondelete SET NULL): the organisation they last worked in, pre-selected on the Select organisation page at their next sign-in.
  - `user.signin_people(otp=None)` lists the people they can sign in as, sorted by organisation name, using `person.can_sign_in()`.
- `Person`: `first_name`, `last_name`, `email`, optional `job_title` and `mobile`, plus:
  - `user_id` (required, ondelete CASCADE), with `UniqueConstraint('organisation_id', 'user_id')`: a user is in an organisation at most once.
  - `can_login` (default False): the organisation's choice. Registration sets it to True.
  - `user_group_id` (ondelete RESTRICT): their permission group in this organisation, see `UserGroup`. Only required when `can_login` is on (`PersonForm.validate_user_group_id`). `person.is_org_admin` is True when it's the Admin group.
  - `person.can_sign_in(otp=None)`: `can_login`, the organisation isn't suspended, and it's verified (or `otp` is the code sent when this person registered it).
  - `Person.email` always equals `person.user.email`. Changing a person's email moves them to the user with that email (`change_person_email()`), never edits the shared user.
- `UserGroup` belongs to an `Organisation` (`organisation.user_groups`, cascade delete) and has `people`. It stores `name` (unique per organisation) and `is_admin`.
  - `UserGroupPermission` rows (`user_group_id` and `permission`, composite PK, no id or timestamps, like a link table) are the permissions it's granted. `user_group.permission_keys` returns them as a set.
  - Registration calls `create_default_groups(org)`, which makes Admin (`is_admin`, full access, can't be renamed, changed or deleted) and Team (every grid permission). The registrant goes in Admin. The seeder does the same: first person Admin, the rest Team.
- `OTP` belongs to a `User` (ondelete CASCADE, `user.otps`). `person_id` (ondelete SET NULL) is set on codes sent for one organisation (registration and invites): signing in with that code goes there, and a registration code is what verifies a new organisation. It stores `code_hash`, an HMAC-SHA256 of the 6-digit code peppered with `OTP_PEPPER`, never the code itself. It also has `expires_at` and `used_at` (both `DateTime(timezone=True)`, unlike the naive `created_at`/`updated_at`; SQLite returns them naive) and `attempts`.
- `UserSession` belongs to a `User` (ondelete CASCADE, `user.sessions`). It stores:
  - `person_id` (ondelete SET NULL): the organisation the session is working in, as the user's person there. Everything organisation-scoped goes through it (`g.person`). NULL while a user with several organisations chooses one, or for a platform admin outside any organisation.
  - `token_hash`: SHA-256 of the cookie token, unique
  - `expires_at`: 30 days
  - `revoked_at`: set it to log a session out
  - `last_seen_at`: written at most every 5 minutes
  - `user_agent` and `ip_address`: `request.remote_addr`. Behind a proxy or load balancer, this needs Werkzeug's `ProxyFix`. It's named `UserSession` to avoid a clash with Flask's `session` and `db.session`.
- **Addresses**: `Location`, `Supplier` and `Organisation` have one optional `address` (`String(500)`, lines separated by `\n`; it replaced six separate fields, line one to post code, on 2026-11-02). The form has a textarea and saves it through `clean_address()` (`services/addresses.py`: each line trimmed, blank lines dropped, None when empty). Overviews show it with `white-space: pre-line`. The data export has one Address column (a multi-line cell). The locations and suppliers imports have one `address` column (Column kind `address`), where commas separate the lines and are dropped, e.g. `1 High Street, Leeds, LS1 1AA`. It isn't on the index pages or downloads.
- **Locations** (replaced Site, Building and Zone on 2026-11-03 at the user's request): `Location` (`name` up to 100, optional `address` and `telephone`, `organisation_id`, `import_event_id`) nests to any depth through `parent_id` (self-referencing, ondelete CASCADE; `location.parent`, `location.children` by name with ORM `cascade='delete'`). Deleting a location deletes every location inside it and the assets, jobs and job schedules at all of them (`Location.jobs`/`assets`/`job_schedules`, cascade delete, and their `location_id` FKs are ondelete CASCADE); files are only unlinked. Optional `main_contact_id` (a person in the organisation, ondelete SET NULL; `location.main_contact`, `person.main_contact_locations`) is a searchable select on the location form (`set_main_contact_choices()` in `routes/locations.py`, everyone in the organisation) and shows on the overview, linked with `people.view`; it's in the data export and the locations import (`main_contact`, kind `person`: a full name or `Name (email)`, with a dropdown of people in the Excel template; an email-only column was tried and dropped earlier on 2026-11-03 as unintuitive), not on the index or downloads. Optional `location_category_id` (ondelete SET NULL, `location.location_category`, reference data) says what kind of place it is (Site, Building, Floor...), since nesting is free-form; it's only on the location form, never on the asset, job or job schedule location selects.
  - `materialised_path` (`String(1000)`, set by the app only) is the names from the top down joined with ` > ` (`SEPARATOR` in `services/locations.py`), e.g. `Head Office > Main Building > Ground Floor`, and `str(location)` is it. It's unique per organisation: DB `UniqueConstraint('organisation_id', 'materialised_path')` plus the case-insensitive `path_taken()`, which is what stops duplicate names in the same place (`My Site > My Building` and `my site > my building` clash). Names can't contain `>`, so a path always splits back into its names. `set_path(location)` sets the path from the parent and name and recurses into the children; call it after any rename or move. `path_problem(org_id, name, parent, location=None)` returns `(field, message)` or None: a `>` in the name, a move inside itself or a descendant, a taken path, or a path (including the descendants' new paths) over `MAX_PATH_LENGTH`. Other helpers: `build_path()`, `normalise_path()` (tidies spacing around `>` for typed paths), `find_by_path()`, `descendants()`, `subtree_ids(location)` (a subquery of the location and everything inside it, by path prefix with `startswith(..., autoescape=True)`) and `location_tree()` for the index.
  - `Asset`, `Job` and `JobSchedule` have one required `location_id` (`record.location`). `raise_job()` copies it from the schedule; sub-assets and follow-up jobs start at the parent's location (changeable).
- `Job` is at a `Location`, and optionally to a `JobSchedule` (`job_schedule_id`, ondelete RESTRICT). Optional `estimated_cost` and `actual_cost` (`Numeric(12, 2)` pounds, on `JobForm` with a £ prefix via `money_field()` from `_number_fields.html`) are on the edit page only, not create (the create route ignores them; since 2026-11-03), and show on the overview, the data export and the jobs import, not on tables or index downloads. The create page has a Back button to where it was opened from (`back_url`: the asset's or location's Jobs tab, the parent's Follow Up Jobs tab, or the index), which is also where saving goes.
  - `status` is a key from `JOB_STATUSES` in `app/models.py` (`new`, `unassigned`, `assigned`, `in_progress`, `completed`, `closed`, `rejected`; default `new`, enforced by the `ck_job_status` check constraint). `job.status_label` gives the display text and `jobs/_status_badge.html` renders it as a badge. It's set by the app only, never on `JobForm`. `JOB_FINISHED_STATUSES` (`closed`, `rejected`) are the ones a job doesn't move on from: `overdue_conditions()`, the dashboard's Compliance Risks and the index's `not_closed` filter ("All Open Jobs") leave them out. `ASSIGNED_JOB_STATUSES` (`assigned`, `in_progress`, `completed`) are the ones with an assignee, where Reassign and Add Helpers work. **The workflow (simplified 2026-11-02 at the user's request, after testing a version with a separate `Assignment` per assignee, each accepting, starting and completing independently, with emailed token links; that was dropped as too complex):** New → Approve (to Unassigned) or Reject → Assign (one supplier or one person, plus helpers) → Start → Complete → Close. Everything is on the one job; there are no assignment records.
  - **Approve and reject** (extra permission `jobs.approve`, "Approve or reject new jobs"): while a job is `new`, its header shows Approve, a POST form to `/jobs/<id>/approve` (`jobs.approve`) that sets status `unassigned` and `approved_at` and goes back to the job, and Reject, a link to GET/POST `/jobs/<id>/reject` (`jobs.reject`, also needs `jobs.approve`), whose `JobRejectForm` takes a required `rejection_reason` (Text, up to 2000 characters, shown on the overview and in the data export). POST sets status `rejected`, `rejection_reason` and `rejected_at`, and redirects to `/jobs`. `approved_at` and `rejected_at` (`DateTime(timezone=True)`) show on the overview and in the data export. Both routes refuse a job that isn't new. **Planned jobs can be rejected**: when `job.closes_with_schedule_update`, the reject page shows the schedule and `JobRejectForm(latest=next_due_date(uk_today(), frequency))` asks for a required `next_due_by` (pre-filled with that date; not before today or after it, the same rule as Update schedule via `validate_next_due_by_range()`), and the POST rejects the job and sets the schedule's `next_due_by` and `next_job_creation_date` in one commit. A rejected job has no Close button. A rejected job that isn't planned shows Reopen (`jobs.reopen`, the same route as for closed jobs), which sets status back to `new` and clears `rejected_at` and `rejection_reason`; a rejected planned job can't be reopened (its schedule has moved on).
  - **Assigning** (extra permission `jobs.assign`, "Assign jobs, and start and complete them for the assignee"; routes in `routes/jobs.py`): the job is given to one supplier (`assigned_supplier_id`, `job.assigned_supplier`, `supplier.assigned_jobs`) or one person (`assigned_person_id`, `job.assigned_person`, `person.assigned_jobs`), never both (`ck_job_assignee`); `job.assignee`, `job.assignee_name` and `job.is_assignee(person)`. Both FKs are ondelete RESTRICT with `passive_deletes='all'`, and the relationships need `foreign_keys` (as does `closed_by`), because job has several person FKs. **Helpers** are people in the `job_helpers` link table (both FKs CASCADE; `job.helpers` by name, `person.helping_jobs`): they aren't notified and can't start or complete. `assigned_at` is set by Assign and Reassign. The pages:
    - **Assign** (header button while `unassigned`; GET/POST `/jobs/<id>/assign`, `jobs.assign`, `jobs/assign.html`; refuses any other status): `JobAssignForm` has `assignee`, one select grouped into Suppliers and People (values `supplier:<id>` / `person:<id>`; the route sets a flat `choices` list for validation from `assignee_options()`, and the template renders the optgroups itself), and an optional `helper_ids` multi-select of everyone; the lead can't also be a helper. POST sets the assignee (`give_job_to()`), the helpers and status `assigned`, commits, then `tell_assignee()`.
    - **Reassign** (header button while in `ASSIGNED_JOB_STATUSES`; GET/POST `/jobs/<id>/reassign`, `jobs.reassign`, same template with `JobReassignForm`, no helpers): the choices leave out the current assignee. It changes only the assignee and `assigned_at` (status, dates and helpers stay; a helper made lead stops being a helper), then tells the new assignee. The previous one isn't told.
    - **Add Helpers** (a button next to Helpers on the overview, while in `ASSIGNED_JOB_STATUSES`; GET/POST `/jobs/<id>/helpers/add`, `jobs.add_helpers`, `jobs/add_helpers.html`, `JobHelpersForm`): people not helping already, less the lead. Each helper on the overview has a remove button (`bi-x-circle`, with `jobs.assign`, same statuses): a POST form to `/jobs/<id>/helpers/<person id>/remove` (`jobs.remove_helper`; 404 for someone who isn't a helper on the job). Neither adding nor removing tells anyone.
    - **Who's told** (`notify_assignee(job, assigned_by)` in `services/jobs.py`, called by `tell_assignee()` after the commit; nobody is told when you assign a job to yourself, because the job page the route redirects to would mark it read at once): a person who `can_sign_in()` gets an in-app notification ("<name> assigned you a job: <description>", see `Notification`) and no email; a supplier, or a person who can't sign in, gets `emails/jobs/assigned.html` (the job's details, no links). It returns False when there's no email address (suppliers' is optional), and the route flashes a warning; a failed email is logged and flashed. Either way the job stays assigned.
  - **Start and Complete** are for the assignee (a person) or someone with `jobs.assign` doing it for them: the jobs blueprint uses `require_job_permission` instead of `require_permission`, which lets the job's assigned person through to `ASSIGNEE_ENDPOINTS` (`jobs.view`, `jobs.start`, `jobs.complete`) whatever their user group (so someone with no jobs permissions can open a job assigned to them from the notification); everything else, including other people's jobs, goes through `require_permission` as usual. The header shows Start while `assigned` (POST `/jobs/<id>/start`: status `in_progress`, `started_at` now) and Complete while `in_progress` (GET/POST `/jobs/<id>/complete`, `jobs/complete.html`, an info alert when it's on someone's behalf): `JobCompleteForm` takes `completed_at` (date and time, UK, default now, stored with the time zone via `completed_at_uk()`; not in the future, not before the minute it started) and required `completion_comments` (Text, up to 5000), and sets status `completed`. Both refuse any other status.
  - The overview shows Assigned To (linked with `suppliers.view` / `people.view`), Helpers (linked with `people.view`) and Add Helpers, Assigned At, and Completion Comments; the data export has Assigned To, Assigned Supplier ID, Assigned Person ID, Helpers, Helper IDs, Assigned At (UTC) and Completion Comments.
  - **Assigned To column** (`data-col="assigned_to"` in `jobs/job_list.html`, "Assigned to" on the mobile cards when set, and `JOB_COLUMNS` for downloads): `job.assignee_name`. `filtered_jobs()` selectinloads the assigned supplier and person.
  - `source` is a key from `JOB_SOURCES` (`planned`, `reactive`, `follow_up` ("Follow Up", renamed from `remedial` on 2026-11-02); `ck_job_source` check constraint), shown with `job.source_label`. It's required with no default at any level, so every code path that creates a job must set it: the create route sets `reactive` (or `follow_up` with `?parent_id=`), and raising a job from a schedule should set `planned`. Not on `JobForm`.
  - **Follow-up jobs**: `parent_job_id` (self-referencing, ondelete SET NULL; `job.parent_job`, `job.follow_up_jobs` by `created_at`), set only at creation and never changed. They're created from the parent's **Follow Up Jobs** tab: its Create Follow Up Job button (with `jobs.create`, any status; on 2026-11-02 this replaced a Follow Up Work Required box on Complete, which an assignee without `jobs.create` couldn't use) links to `/jobs/create?parent_id=<id>` (`org_get_or_404`), which says it's follow-up work, pre-fills the parent's location (changeable), and on POST saves the job with source `follow_up`, status `new` and the parent, then redirects to the parent's Follow Up Jobs tab (`jobs.follow_up_jobs`, `/jobs/<id>/follow-up-jobs`, needs view, `jobs/view/follow_up_jobs.html` through `job_list.html`, searched and paginated). The follow-up job's overview shows Parent Job, linked; the data export has Parent Job ID. Deleting the parent leaves its follow-ups without one. The seeder makes a few, at the parent's location.
  - `closed_at` (Date, nullable) and `closed_by_id` (the person who closed it, ondelete SET NULL; `job.closed_by`, `person.closed_jobs`; shown as Closed By on the overview, linked with `people.view`, and in the data export as Closed By and Closed By ID) are set only by closing. **A job can only be closed once it's `completed`**, so a closed job always has a record of the work: the close and update schedule routes refuse any other status (`not_completed_warning()`). The header shows Close (with `jobs.close`) only while the job is completed: a POST form to `/jobs/<id>/close` (`jobs.close`, POST only, no close-date page) that sets status `closed`, `closed_at` to the UK date and `closed_by`. For a job where `job.closes_with_schedule_update` is True it saves nothing and redirects to Update schedule below. An already-closed job redirects back with a warning. A closed job that isn't planned shows a Reopen button instead: a POST form to `/jobs/<id>/reopen` (`jobs.reopen`, needs `jobs.reopen`, POST only) that sets status `completed` and clears `closed_at` and `closed_by`. `started_at` and `completed_at` (`DateTime(timezone=True)`, set by Start and Complete) show on the overview in UK time and in the data export as `Started At (UK)` and `Completed At (UK)` (via `as_uk()`).
  - **Sequence rules for planned jobs** (each close or reject sets the schedule's next due date, so these keep a schedule to one open job in order; the support guide explains them to customers):
    - a closed or rejected planned job can't be reopened (route refuses, Reopen button hidden)
    - an open planned job can't be deleted (GET and POST refuse, Delete button disabled); a closed or rejected one can
    - a planned job's `due_by` can't be edited: the edit page shows it read-only and the route ignores the field
    - a job schedule that has raised any jobs can't be deleted (GET and POST refuse, Delete button disabled). Deleting a location still cascades through its schedules and jobs.
    - backstop: the partial unique index `uq_job_open_per_schedule` on `job (job_schedule_id) WHERE status NOT IN ('closed', 'rejected')` (in `Job.__table_args__`) means the database refuses a second open job on a schedule, whatever the app does. A breach raises `IntegrityError`; in the daily run it's rolled back and logged like any other failure. The seeder keeps to it too: a schedule gets at most one open job, and that schedule's `next_job_creation_date` is NULL, as after `raise_job()`.
  - **Update schedule** (GET/POST `/jobs/<id>/update-schedule`, `jobs.update_schedule`, needs `jobs.close` rather than `job_schedules.edit`, because it's part of closing) is the second step of closing a planned job. `job.closes_with_schedule_update` is True for a planned job whose schedule's `next_job_creation_date` is NULL, meaning `raise_job()` is waiting on it. The page shows the schedule (description, frequency, location) and offers `next_due_date(job.completed_on, frequency)` as the next due date: the date the work was completed, not closed, plus the frequency. `JobScheduleNextDueForm` refuses a date before today or after that calculated date (or after today, when the calculated date has already passed). POST closes the job today (status, `closed_at`, `closed_by`) and sets the schedule's `next_due_by` and `next_job_creation_date` in one commit, so a job is never closed with its schedule left waiting. There's no skip: leaving the page leaves the job open. A closed job, or one that doesn't close with a schedule update, redirects to the job with a warning.
- `Notification` (`organisation.notifications`, cascade delete): an in-app message to a person who can sign in. `message` (255), `read_at`, `person_id` (required, ondelete CASCADE) and optional `job_id` (ondelete CASCADE; what its View button opens, via `notification_url()`). The relationships are one-way (`notification.person`, `notification.job`, no backrefs), so the ORM never clears them and the database cascades. `services/notifications.py`: `notify(person, message, job=None)` (doesn't commit), `person_notifications()`, `unread_notifications()`, `mark_read()`. Opening a job (`jobs.view`) marks your notifications about it read. Not in `DELETE_ITEMS` (they're part of their people). People and suppliers assigned to jobs are kept for audit: their delete routes refuse on GET and POST (mentioning archiving will come later), the view header's Delete button is disabled, and import undo of them is blocked (`undo_blockers()`); `delete_organisation()` clears every job's assignee before deleting people, because of the RESTRICT. Archiving isn't built yet.
- `JobSchedule` is at a `Location` and has many `jobs`. Optional `estimated_cost` (pounds) and `estimated_duration` (`Numeric(6, 2)` days, so 0.5 is half a day; `number_field()` with step 0.25, shown with the `days` filter) are on the form, overview, data export and the job schedules import (`money` and `days` column kinds), not on tables. Copy copies both, and `raise_job()` copies `estimated_cost` to the job. `next_due_by`, `frequency` (a key from `FREQUENCIES` in `app/services/scheduling.py`; `job_schedule.frequency_label` gives the display text) and `notice_days` (0–365, and no more than the frequency's shortest gap in `FREQUENCY_MIN_DAYS`, checked by `JobScheduleForm.validate_notice_days`) are required. The view header's Copy button (shown with `job_schedules.create`) links to `/job-schedules/create?copy_from=<id>`: GET pre-fills description, work required, frequency, notice days, statutory compliance and active from that schedule (`org_get_or_404`). Next due (deliberately: it should be chosen, not carried over), location and linked assets aren't copied, and the new schedule keeps no link to the original. After create, a user with `job_schedules.edit` goes to `/job-schedules/<id>/created` (`job_schedules.created`, needs view), which says it's saved and asks whether to add assets now: Yes goes to `link_assets`, No to the index. Without edit, create flashes and goes straight to the index. `next_job_creation_date` is never on a form: create and edit set it with `job_creation_date(next_due_by, notice_days)`. It can be in the past when the due date is close. It's NULL once a job has been raised for `next_due_by` (see `raise_job()`). `is_active` (default True, on the form as "Active") turns the schedule off: `due_job_schedules()` skips inactive schedules, so they raise no jobs. `check_reactivation()` in `routes/job_schedules.py` makes an edit that turns it from inactive to active have a `next_due_by` after today. The job schedules import has an optional `active` Yes/No column (`Column(..., blank_means_yes=True)`), so a blank cell or a file without the column imports active schedules. Reactivation's future-date rule doesn't apply to imports, which only create. `job_schedule.next_job_creation_label` is how pages and the index download show Next Job Creation: "Inactive", "Pending current job closure" (NULL) or the date. `job_schedule.open_job` is the schedule's job that isn't closed, or None. Edit (GET and POST) redirects to the view with a warning while there is one, so a schedule never has two open jobs; the header's Edit button is disabled and the overview shows an alert linking to the job and to the support guide. Because of that, edit always recalculates `next_job_creation_date`, which also restarts a schedule whose open job was deleted.
- `Asset` is at a `Location`. `asset_number` and `serial_number` are optional (blank stored as NULL) and each unique per organisation: there's a DB `UniqueConstraint` with `organisation_id`, and `check_unique()` in `routes/assets.py` checks case-insensitively and adds form errors. It links many-to-many to jobs (`job_assets` table) and to job schedules (`job_schedule_assets` table). The link FKs use ondelete CASCADE, so deleting a record removes only its link rows. `assigned_to_id` (ondelete SET NULL) is the person it's assigned to (`asset.assigned_to`, `person.assigned_assets`), set only on the Assign page: the view header's Assign button (with `assets.edit`) goes to GET/POST `/assets/<id>/assign` (`assets.assign`, needs `assets.edit`), a select of every person in the organisation plus Unassigned (`AssetAssignForm`, so WTForms refuses anyone else). The overview shows Assigned To, linked to the person with `people.view`. It's in the assets data export and the assets import (`assigned_to`, kind `person`: a full name or `Name (email)`, since 2026-11-03), not on `AssetForm` or the index. Deleting the person (by hand or by undoing a people import) just leaves their assets unassigned; that's intended (decided 2026-11-03), so don't add an undo blocker for it. `parent_id` (self-referencing, ondelete SET NULL; `asset.parent`, `asset.sub_assets` by description) makes it a sub-asset. It's only set at creation from the parent's Sub-Assets tab (`assets.sub_assets`, `/assets/<id>/sub-assets`, needs view): its Create Sub-Asset button (with `assets.create`) goes to `/assets/create?parent_id=<id>` (`org_get_or_404`, so another organisation's asset is a 404), which pre-fills the parent's location (changeable) and redirects back to the tab. The parent never changes, so there are no loops; sub-assets can have sub-assets. The regular create form and `AssetForm` have no parent field. Deleting a parent makes its sub-assets top-level (the delete page warns). The overview shows Part Of, and the export has Part Of Asset ID. The index and import don't show or set it.
- `ImportEvent` records one CSV import. It stores `import_type` (a key from `IMPORT_TYPES`), `filename`, `rows_imported`, `errors` (JSON `[{'row', 'error'}]`, with the header as row 1), the organisation, `imported_by_name`, and `undone_at`/`undone_by_name`. The names are copied from `person.full_name` at the time, not foreign keys, because person has `import_event_id` (see No circular foreign keys), and so they survive the person being deleted. `Location`, `Asset`, `JobSchedule`, `Job`, `Supplier` and `Person` have a nullable `import_event_id` (ondelete SET NULL) set on imported records.
- `File` (`organisation.files`, cascade delete): `description` (required), optional `expires` (`file.is_expired` against the UK date), `size_mb` (Numeric, summed for Storage Used), `filename` (as uploaded, for downloads), `content_type` (from the extension via `FILE_TYPES`, never from the browser) and `storage_key` (unique, `<organisation id>/<file id>.<ext>`). Only `description`, `expires` and `file_category_id` can be edited (`files.edit`); the stored file, `filename`, `content_type`, `size_mb` and `storage_key` never change, so replacing a file means uploading a new one. Link tables `location_files`, `job_files`, `asset_files`, `job_schedule_files`, `person_files` and `supplier_files` (both FKs ondelete CASCADE) give `file.locations`... and `<record>.files` (by description). Deleting a record only removes its link rows; deleting a file (`delete_files()`) removes it from storage too.
- **Reference data** (categories and conditions): `JobCategory`, `AssetCategory`, `AssetCondition`, `LocationCategory`, `SupplierCategory` and `FileCategory` share the `ReferenceItem` mixin in `models.py`: `description` (100 chars, unique per organisation by `UniqueConstraint` plus case-insensitive `find_item()` checks) and `organisation_id` (cascade delete from `Organisation`; they're in `DELETE_ITEMS`). `str(item)` is its description, so templates show `{{ asset.asset_category or '-' }}`.
  - Records point at them with optional FKs (ondelete SET NULL) and a relationship of the same name: `Job.job_category`, `JobSchedule.job_category`, `Asset.asset_category`, `Asset.asset_condition`, `Location.location_category`, `Supplier.supplier_category` and `File.file_category` (on upload and file edit).
  - `Asset` has `condition_set` (Date), set by the app only: `set_condition(record, column, condition_id)` (`services/reference_data.py`) sets it to `uk_today()` when the condition changes on create or edit, clears it when the condition is cleared, and leaves it otherwise. It's shown on overviews, never on a form.
  - `raise_job()` copies the schedule's job category to the job, and Copy (`?copy_from=`) pre-fills it.
- **Support tickets**: `SupportTicket` (`description` Text, `status` a `SUPPORT_TICKET_STATUSES` key, `open`/`closed` with the `ck_support_ticket_status` check, set by the app only; `ticket.status_label`) belongs to an organisation (cascade delete, deliberately not in `DELETE_ITEMS`: they're the platform's records, so they go with the organisation without a box to tick) and has `created_by` (a person, ondelete SET NULL, `person.support_tickets`, so deleting the person keeps the ticket). `SupportTicketNote` (`description`, `created_by` a `User`, ondelete SET NULL) belongs to the ticket (`ticket.notes`, oldest first, cascade delete); like `UserGroupPermission` it has no `organisation_id` of its own.
- Every model has `id`, `created_at` and `updated_at`.
- History: these were renamed from WorkOrder → Job, PPMSchedule → JobSchedule, Contractor → Supplier, and Site, Building and Zone were replaced by one nested Location on 2026-11-03 (with them went the building condition reference type and the sites/buildings/zones imports). Old names should not appear anywhere.
- Migrations: **`0a96054ef8b7_init.py` predates the Location change (2026-11-03) and needs regenerating** (a scratch autogenerate of the new models was clean: no `use_alter`, 75 of 75 FKs inline). A regenerated initial migration (currently `0a96054ef8b7_init.py`, regenerated by the user on 2026-11-02 after the `due_by` rename, the single `address` field and the removal of the circular foreign keys below; used as generated, with no hand edits). It's pre-production, so the user usually deletes and regenerates migrations rather than stacking them. **No circular foreign keys** (decided 2026-11-02, so a regenerated migration is right with no hand edits): tables must be creatable in one order, each after every table it refers to. Autogenerate writes a `use_alter` foreign key inside `create_table`, where Postgres silently leaves it out (SQLite keeps it, so scratch tests don't notice), and that was missed on regenerations. So organisation (terms) and import events (imported and undone by) store the person's name rather than a person id. Don't add a foreign key that would close a loop (for example a person column on a table person already refers to, such as organisation or import_event); copy what's needed, as these do. Check after regenerating: `DATABASE_URL=postgresql://x:y@localhost/z flask db upgrade --sql | grep -c "FOREIGN KEY"` should equal the models' count, and `grep use_alter migrations/versions/*.py` should find nothing. Both need no database.

## Code layout and conventions

- Routes: one blueprint per resource in `app/routes/`: `locations`, `assets`, `jobs`, `job_schedules` (URL `/job-schedules`), `suppliers`, `people`, `user_groups` (URL `/user-groups`), plus `my_organisation` (URL `/my-organisation`), `files` and `notifications` (see Notifications). All are registered in `app/__init__.py`. URLs use hyphens; endpoints and templates use underscores.
- `organisations` blueprint (`/organisations` prefix) holds `register()`, but that view is mounted at the root `/register` (`/login` is mounted the same way, see `auth` below) with `app.add_url_rule(..., endpoint='organisations.register')` in `create_app`, so `url_for('organisations.register')` gives `/register`. `terms()` (`organisations/terms.html`, a placeholder for now) is mounted the same way at the public `/terms`, and `RegisterForm.accept_terms` is a required checkbox linking to it (registration records it in `terms_accepted_at`, `terms_accepted_by_name` and `terms_accepted_by_email`). Registration creates an Organisation and an admin Person (with `can_login`) in one commit. The email is stripped and lowercased; an email that already has a user reuses it (`find_or_create_user()`), so one login can register several organisations, after a rate-limit check on that user. The organisation starts with `verified_at` NULL: anyone can type any email here, so it isn't offered at sign-in or in Switch organisation until the code sent now (`create_otp(user, person)`, which carries the person) is entered, and `choose_person()` then sets `verified_at`. It redirects to the validate page. If sending fails it still goes there, with a warning to use "Send a new code", which keeps the organisation.
- **People** (`/people`, `app/routes/people.py`):
  - Index, view, create, edit and delete like the other resources, gated by the `people.*` permissions like everything else.
  - The form has a required User Group select, built from `org_query(UserGroup)`. Non-admins don't see the Admin group in the list, can't edit, delete or resend to an admin (`require_can_manage`, 403), and can't change their own group.
  - The organisation must always have at least one admin who can log in (`other_active_admins(person)`). Edit refuses to move the last one out of Admin or turn off their login, and delete refuses to remove them.
  - After an edit, if you can no longer see people (you moved yourself to a smaller group), you're sent to the dashboard.
  - Templates: tabbed `people/view/` (Overview, and Assets: the person's `assigned_assets` through `asset_list.html`; the Assets tab and `people.assets` also need `assets.view`, so the tab is hidden and the route gives a 403 without it) and an inline table in `index.html`. The search covers first, last and full name, email and job title.
  - Create lowercases the email. `email_in_organisation()` refuses an email already used by someone in this organisation. Other organisations don't matter: an email with a user elsewhere links to that user (`find_or_create_user()`), with the same response as a new one, so the form never reveals that an email has an account.
  - Edit: changing the email calls `change_person_email()` (`services/people.py`), which moves the person to the user with the new email (creating it), ends the person's sessions here, and deletes the old user if nothing else uses it. It never edits a user's email, because the user may be in other organisations (otherwise one organisation could change Bob's email to its own address and sign in as Bob elsewhere). Changing your own email signs you out.
  - Turning `can_login` on, or changing the email of someone who can log in, calls `send_invite()`: it checks the rate limit, then `create_and_send_otp(person.user, person, invited_by=<name>)`, whose subject is "<name> added you to <organisation> on MyFmHub", and flashes the outcome. Adding someone without login sends nothing. Turning login off calls `revoke_person_sessions(person)`, which ends only the sessions working in this organisation.
  - POST `/people/<id>/send-invite` (needs `people.edit`) is the "Resend sign-in email" button on the view page. It shows when `can_login` is on and it isn't your own record, and it calls `send_invite()`.
  - Delete calls `delete_person()`: it ends the person's sessions here, deletes the person, and deletes their user only if this was their last person (and they aren't a platform admin).
  - Nobody can remove their own `can_login` or delete themselves.
- **Permissions** (`app/services/permissions.py`):
  - Keys are `<resource>.<action>`. `RESOURCES` (locations, assets, jobs, job_schedules, suppliers, people, files) × `ACTIONS` (view, create, edit, delete), less `NOT_GRANTABLE` (grid cells shown as n/a; empty at the moment), plus `EXTRA_PERMISSIONS` (`jobs.approve`, `jobs.assign`, `jobs.close`, `jobs.reopen`, `imports.manage`, `exports.manage`, `reference_data.manage`, listed under the grid), make up `GRANTABLE`, the grid on the user group pages.
  - `ADMIN_ONLY` (`organisation.manage`, `sessions.manage`, `user_groups.manage`) is never stored on a group: only the Admin group has these.
  - `can(person, key)`, called with `g.person`: the Admin group always passes, otherwise the key must be in the person's group's `permission_keys`. Templates use the global `can('jobs.edit')` (the signed-in user in the session's organisation) to hide buttons and navbar links.
  - `clean_permissions()` drops unknown and admin-only keys, and adds `<resource>.view` whenever create, edit or delete is given. `set_permissions(group, keys)` applies the difference.
  - **Enforcement**: every resource blueprint and `user_groups` registers `before_request(require_login)` then `before_request(require_permission)`. `require_permission` looks up `request.endpoint` in `ENDPOINT_PERMISSIONS` and gives a 403 if the group lacks the permission, or if the endpoint isn't listed. When you add a route to one of these blueprints, add its endpoint to `ENDPOINT_PERMISSIONS` or it will always 403.
  - The convention is: index, view and related tabs need view; create, edit and delete need their own; link and unlink need edit on the record you're on (for example `jobs.link_assets` needs `jobs.edit`).
  - New custom groups start with view on every resource.
  - Any `abort(403)` renders `templates/errors/403.html` through the `errorhandler(403)` in `create_app`. The page says your user group doesn't allow this and links to the dashboard. The suspended-organisation page is a separate, explicit 403 response and isn't affected. Any 404 (unknown URL, `get_or_404`, another organisation's record, `/admin` for non-admins) renders `templates/errors/404.html` the same way, with a dashboard or sign-in button depending on whether you're signed in.
  - Unhandled exceptions render `templates/errors/500.html` (debug off only; debug mode shows Flask's debugger). The handler rolls back the session first. The template is deliberately standalone: it doesn't extend `base.html` or use `url_for`/`g.user`, so it renders even when the database is the problem. Keep it that way.
- **User groups** (`/user-groups`, `user_groups.manage`, so admins only; linked from the navbar dropdown):
  - Index, create, view, edit and delete. Create and edit have a name plus the permissions grid (`user_groups/_permissions_grid.html`, plain `permissions` checkboxes read with `request.form.getlist`).
  - Names are unique per organisation, case-insensitively.
  - The Admin group redirects away from edit and delete. A group with members can't be deleted.
  - People are moved between groups on their person record. The group view lists its members.
- **Auth and tenancy in resource routes**: every resource blueprint calls `<bp>.before_request(require_login)` straight after it's created, so every route needs a signed-in user. Every query goes through `org_query(Model)` or `org_get_or_404(Model, id)` from `app/routes/helpers.py`, which filter by `g.person.organisation_id` (the session's organisation). Never use a bare `Model.query` or `Model.query.get_or_404` in a resource route. A record from another organisation gives a 404.
  - Create routes set `organisation_id=g.person.organisation_id`. Edit routes don't need to, because the record was loaded scoped and `organisation_id` is never taken from a form.
  - Location selects are built from `org_query(Location)` (`set_location_choices()`), and WTForms rejects any `location_id` not in the choices, so another organisation's location can't be assigned. Related tabs use relationships from an already-scoped parent. Link queries also go through `org_query`.
- **Locations pages** (`routes/locations.py`, `templates/locations/`; "Locations" in the main navbar with `locations.view`; `locations` in the permission grid):
  - Index (`/locations/`): with no search or `?import_id=`, every location as a nested tree (`location_tree()`, a recursive `location_branch` macro in `index.html`), each name linking to its page. The tree shows each location's category in brackets. A Category filter (`?location_category_id=`, `filter_reference()`), a search (on the path) or an import filter switches it to a paginated table (Location path, Name, Location Category, Telephone) with Columns and Download (`LOCATION_COLUMNS`, `locations.export`).
  - Create (`LocationForm`: name, optional Parent Location select of every location by path, optional Location Category, optional Main Contact, address textarea, telephone) runs `check_path()` (`path_problem()`), saves with `set_path()` and redirects to the tree. `?parent_id=` pre-selects the parent: the view header's Add Sub-Location button (with `locations.create`).
  - Edit can rename and move (change the parent). `set_parent_choices(form, location)` leaves out the location and its descendants, and `path_problem()` refuses them too; saving calls `set_path()`, which rewrites every descendant's path.
  - View: tabs Overview (name, Parent Location linked, telephone, address, Sub-Locations), Jobs, Job Schedules, Assets and Files (`locations/view/`). The Jobs, Job Schedules and Assets tabs list records at the location **and every location inside it** (`in_location(Model, location)` in helpers, through `subtree_ids()`).
  - Delete: the GET page warns that every location inside it and all their assets, jobs and job schedules go too, with counts; POST deletes through the ORM cascade.
- **Location selects** (`templates/_location_fields.html`, helpers in `routes/helpers.py`): asset, job and job schedule forms render `{{ location_fields(form) }}`, one searchable `location_id` select (`reference_select`) whose options are every location's `materialised_path` (`set_location_choices(form)`, sorted by lower-case path via `org_locations()`); store it with `parse_uuid(form.location_id.data)`. Every `select.form-select` (forms and index filters) is made a Tom Select by `app.js` (`allowEmptyOption`, `maxOptions: null` so long lists aren't cut at 50, and the `remove_button` plugin on a `multiple` select; `data-no-search` opts one out). The native select stays in the form and is what's submitted; if the CDN fails, the selects stay plain. Give any new select the `form-select` class to get search. Every searchable select (single and multiple, e.g. job helpers) uses Tom Select's `dropdown_input` plugin (in the complete build already loaded), so the search box is at the top of the dropdown and typing never sits next to the current choice; that's why the "none" choices keep their labels ('-', '--- Select Location ---', '--- None (top-level location) ---'...). Blank labels were tried and reverted on 2026-11-03. `reference_select()` shows a field's `description` as form text.
  - Index filters use `{{ location_filters(locations, location_id) }}` with `**location_options()` from the route, and `filter_location(query, Model)` in `filtered_<x>()` applies `?location_id=`, matching the location and everything inside it. The list tables and downloads have one Location column (`data-col="location"`, the path), mobile cards show it with `location_text(record)`, and overviews show it with `location_lines(record)`, linked with `locations.view`.
  - Link pages offer records in the same top-level location (the site) as the record you're on: `same_top_location(Model, location)` in helpers.
  - **Creating from a tab** (added 2026-11-03): an asset's Jobs and Job Schedules tabs have a Create button next to Link (with `jobs.create` / `job_schedules.create` and `assets.edit`) to `/jobs/create?asset_id=` / `/job-schedules/create?asset_id=`, and a location's Jobs, Job Schedules and Assets tabs have one (with the create permission) to `?location_id=`. `create_from(allow_asset=True)` in helpers returns `(asset, location)` (404 for another organisation's, 403 for `?asset_id=` without `assets.edit`); the route sets `form.location_id.data` to that location on GET and POST, so whatever is posted is ignored, and `location_fields(form, fixed_location)` renders no select while `location_notice()` says where it will be. Saving links the asset (for `?asset_id=`) and redirects to the tab it came from (`assets.jobs`, `assets.job_schedules`, `locations.<tab>`); a schedule created this way skips the `created` page. `assets.create` only takes `?location_id=`. With `?asset_id=` or `?location_id=`, a job's `?parent_id=` or an asset's `?parent_id=` no longer sets the location.
- **Layout**: `base.html` and the navbar use `container-fluid px-3 px-lg-4`, so tables get nearly the full screen width. **Forms** are two columns on desktop and one on mobile: the fields sit in a `<div class="row">`, each in `<div class="col-md-6 mb-3">` (a checkbox puts its `form-check` inside the column). A form with one input still uses one half-width column, so nothing stretches across the page. `location_fields()` and `reference_select()` render columns, so call them inside the row. Anything wide, like the user group permissions grid, goes after the row. Give new forms the same structure.
- Page titles: every page template sets `{% set title = '...' %}` straight after its `extends` line (outside any block, so `base.html` can see it), and `base.html` renders "MyFmHub - <title>", or just "MyFmHub" when it's unset (the dashboard). Tabbed views set it once in `view/_layout.html` from the record, e.g. "Site: <name>". Give every new page one.
- Every resource has the standard routes: `index`, `create`, `view`, `edit`, `delete`. Delete is GET for a confirmation page and POST to delete, with a hidden `csrf_token` input.
- Related-data tab routes sit under a `### RELATED DATA ###` comment in each route file. For example `/assets/<id>/jobs` renders `assets/view/jobs.html` with `active_tab="jobs"`.
  - **Search and pagination**: every related tab (Files tabs too) and every link/unlink page (files link and remove too) searches and paginates like an index page. The route builds a query and calls `related_page(query, Model)` from helpers, which applies `?search=` to the model's columns in `RELATED_LISTS` (with its sort order) and paginates 25 a page, returning `(pagination, search)`. Tabs get their query from `related(record, Asset.jobs, Job)` (or `in_location()` for a location's tabs) (`with_parent`, through `org_query`), and pass the list as `pagination.items`, not the relationship. Templates import `related_search` from `_related_search.html` (the search box, hidden while there's nothing to search) and `pagination_nav`, and show three states: results, "No X match your search." and the empty message. Unlink buttons on tabs show with `pagination.total or search`, so the relationship isn't loaded. Add new models to `RELATED_LISTS`.
- **Index search forms** with filters (jobs, job schedules, and assets in `assets/search_form.html`) show only the search box, Search, Cancel and an Advanced button on the first row. The other filters sit in a Bootstrap collapse (`#advanced-filters`) that starts open (`advanced_open`) when any of them is set, so a dashboard card's filtered link shows why the list is filtered. When you add a filter, add it to that page's `advanced_open` too.
- **Index pages** paginate with `query.order_by(<field>, Model.id).paginate(page=page, per_page=25, error_out=False)`. The `id` tie-breaker is needed because the sort field isn't unique. Templates import `pagination_nav` from `pagination.html` and show three states: results, "No X match your search." (when a search or site filter is active) and "No X yet."
- **Imports** (`/imports`, `app/routes/imports.py`, `services/imports.py`; "Import data" in the navbar dropdown):
  - Everything here needs the extra permission `imports.manage` ("Import data"). It covers importing every type, whatever else the group allows. Undo also needs delete on that type (`import_type.delete_permission`, e.g. `locations.delete`): the Undo button is hidden and the route gives a 403 without it, so importing doesn't become a back door to deleting records later. Types: locations, assets, people, suppliers, job schedules, jobs, in `IMPORT_TYPES`. Jobs (added 2026-11-03, `create_job()`): `description`, `work_required`, `location` required; optional `due_by`, `status` (kind `job_status`: key or label, blank means `new`), `assigned_to` (kind `assignee`: a supplier's name or a person's full name, ignoring case and spacing, which must match exactly one of either, via `Lookups.by_name()`), `helpers` (kind `helpers`: comma-separated person full names, each matching exactly one person, not the assignee), `job_category`, `statutory_compliance`, `estimated_cost`, `actual_cost`. Imported jobs are always source `reactive`; assigned, in progress, completed and closed need an assignee, and new, unassigned and rejected can't have an assignee or helpers. Nobody is notified, and the workflow dates (`approved_at`, `assigned_at`, `started_at`, `completed_at`, `closed_at`) stay blank. Helpers are set by `job_saved()` after the row's savepoint (a relationship set before it would pull the job into the session early). Undo has no extra blockers (deleting a job only unlinks follow-ups, assets and helpers). Locations: `name` (no `>`), optional `parent` (a path, Column kind `location`), `address`, `telephone`, `location_category`; the new path must not be taken (against the database and earlier rows, ignoring case), and a parent can be a location added by an earlier row: `create_location()` gives the new location its id up front and `ImportType.saved` (`location_saved()`) adds it to `Lookups.locations` once its savepoint commits. Assets and job schedules have a required `location` column (kind `location`): the full path, matched ignoring case and the spacing around `>` (`normalise_path()`). Undo of locations is blocked while any imported location has assets, jobs or job schedules, or has a child that wasn't in the same import. Each lists `Column`s (key, kind, required, max length, notes); the guidance page and the template CSV (`/imports/new/<slug>/template.csv`) are generated from them.
  - Categories and conditions are optional `reference` columns (`reference(key, Model)`): `job_category` on job schedules, `asset_category` and `asset_condition` on assets, `location_category` on locations, `supplier_category` on suppliers. The value must match an existing item's description, ignoring case (`Lookups.reference_item()`), or it's a row error; imports never create them. Assets also take `condition_set` (a date): `condition_fields()` uses the import date when a condition is given without one, and refuses a date with no condition or in the future.
  - `/imports/new/<slug>` shows the guidance and the upload form (`ImportForm`, `.xlsx` or `.csv`). `read_file()` reads either into the same `(row number, {key: cell text})` rows, so every check is shared (`read_rows()`), and refuses the whole file, with nothing saved and no event, for unknown, duplicate or missing required headers, no rows, more than 5,000 rows or more than 5 MB. A CSV is decoded as UTF-8 (BOM allowed), falling back to Windows-1252 for Excel. An `.xlsx` (added 2026-11-03) is read by `read_xlsx()` in `services/spreadsheets.py`: the first sheet only, cached values not formulas (`data_only`), refused if it unzips to more than `MAX_UNZIPPED_BYTES` (50 MB, a zip-bomb guard) or isn't a zip (old `.xls`, password-protected); trailing blank header cells are dropped; `cell_text()` turns Excel's types into the text a CSV cell would have (dates as `yyyy-mm-dd`, whole floats without `.0`, booleans as Yes/No).
  - **Templates**: "Download the Excel template" (`imports.template`, `/imports/new/<slug>/template.xlsx`) is built fresh per download by `template_workbook()`: the header row, a comment on each header (required or optional, the format and the notes), column formats (`TEMPLATE_FORMATS`: text `@` for text columns so `00123` and phone numbers keep their zeros, `dd/mm/yyyy` for dates...), and a dropdown on every column `column_choices()` gives a list for, from a hidden `Lists` sheet (`template_xlsx()`). Fixed lists (Yes/No, frequency, job status) are strict; lists of the organisation's records (location paths, reference items, user groups, assignees) only warn, since they can be out of date by import time and the import checks every value anyway. **The template contains organisation data, so each list only includes what the user can already see**: locations need `locations.view`, assignee suppliers `suppliers.view` and people `people.view`, and the Admin group is left out for non-admins. Helpers have no dropdown (one cell holds several names). Values starting with `=` are written as text (`set_text()`), never formulas. The CSV template (`imports.template_csv_file`, `template.csv`) is still offered, as just the header row.
  - **People in import cells**: a person can be written as their full name or as `Name (email)` (`PERSON_WITH_EMAIL`, `Lookups.people_matching()`), which is how the template's assignee dropdown shows them; the email decides, so people who share a name can be told apart. - `require_login()` / `login_required` (in `app/routes/helpers.py`) redirect to `/login`. GET requests add `?next=<full path>`. POSTs don't, and nothing is changed. They also need `g.person`: a signed-in user with no organisation chosen goes to Switch organisation (with `next`), and a platform admin with none to `/admin`. `require_user()` / `user_required` only need a signed-in user (Switch organisation; `require_platform_admin` uses it too).
  - `login` passes `next` on to the validate URL, and `validate` redirects to it after a correct code, falling back to the dashboard.
  - `next` is always checked with `safe_next_url()`, which allows only local paths (no `//`, backslashes or other hosts).
  - The validate link in emails has no `next`.
  - The dashboard uses the decorator. Resource blueprints use the hook.
- Navbar: when signed in, a `bi-person-circle` icon opens a dropdown with the name, email, current organisation, Switch organisation (when there's another), and a Sign out button (a POST form). When signed out, it shows a Sign in link.
- `dashboard` blueprint: `/dashboard/` renders `dashboard/index.html`. It's the landing page after login.
  - With `jobs.view`, it shows five job cards in one row on wide screens: Compliance Status (green tick, or red with the number of overdue statutory jobs), Compliance Risks (statutory, not closed, due today to 7 days ahead), Overdue Jobs, New Jobs and Unassigned Jobs (status `unassigned`, linking to `/jobs?status=unassigned`).
  - Each card links to `/jobs` with filters that give the same count, so keep the dashboard queries and the `jobs.index` filters in step. Overdue is `overdue_conditions(uk_today())` in `services/jobs.py`, used by both. The jobs Status filter has a filter-only `not_closed` option. `/` (endpoint `dashboard.root`, mounted in `create_app` like `/register` and `/login`) redirects to it.
- People who can log in need a group: call `create_default_groups(org)` and pass `user_group=admin` or `team` (and `can_login=True`, and a `user`) when creating a `Person` directly, and post `user_group_id` in person forms. A seeded or test organisation needs `verified_at` set, or nobody can sign in to it.
- Testing signed-in routes: create a session with `create_session(user, person)` inside `app.test_request_context()`, then `client.set_cookie('auth_session', token, domain='localhost')`. Or sign in for real: patch `app.services.auth.send_email` to capture the code, and patch `check_otp_rate_limit` in the route modules that import it, or repeat sign-ins within a minute are refused. Test emails need a real-looking domain such as example.com: `email-validator` rejects `.test`.
- Testing auth with `app.test_client()`: the auth cookie is Secure, so pass `base_url='https://localhost'` on requests. Flask's own `session` cookie (flash messages, CSRF) is set too, so look for `auth_session` specifically.
- Email templates live in `templates/emails/<area>/` as standalone HTML with inline styles (they don't extend `base.html`).

## Testing

There's no test suite yet. Changes have been checked with throwaway scripts against SQLite, never the dev Postgres database:
- Set `DATABASE_URL=sqlite:///<scratch path>/x.db`. An environment variable overrides `.env`.
- Run `db.create_all()`, then `seeder.py`, then use `app.test_client()` with `WTF_CSRF_ENABLED = False`.
- Postgres UUID columns work on SQLite through SQLAlchemy's generic UUID fallback. One catch: SQLite rejects string IDs assigned to UUID columns (`'str' object has no attribute 'hex'`), for example a str id assigned in a create or edit route. Postgres accepts them, so treat that error as a test-setup artifact, not an app bug. To test successful form saves anyway, patch the bind processor before `create_app()`: wrap `sqlalchemy.sql.sqltypes.Uuid.bind_processor` so its processor converts a `str` with `uuid.UUID(value)` first.

## Known gaps / feature backlog

- **Files export**: the zip is built by a thread in the web server, in a temporary file, so it uses the web instance's memory, CPU and disk while it runs, and a deploy or restart part-way through fails it (the user asks again). If exports become common or very large, move it to a worker.
- **Raising jobs from schedules**: `flask create-jobs-for-job-schedules` (`app/commands.py`) calls `create_scheduled_jobs()` in `services/jobs.py`. It's meant to run once a day from a DigitalOcean App Platform cron job.
  - It picks schedules with `next_job_creation_date <= uk_today()`. It uses `<=` so a missed run or a creation date already in the past is still caught. NULL never matches, so a schedule has at most one job raised and waiting at a time, and one run raises at most one job per schedule.
  - "Today" is the UK date (`Europe/London` via `zoneinfo`, which needs the `tzdata` package on Windows), never the server's UTC date, so BST doesn't shift which day a schedule falls on.
  - `raise_job()` copies description, work required, statutory compliance, location, job category, estimated cost, organisation and linked assets. It sets `due_by` from `next_due_by`, `job_schedule_id`, status `new` and source `planned`. It leaves `next_due_by` unchanged and sets `next_job_creation_date` to NULL. The schedule moves on when the job is closed, through Update schedule (see `Job`), using `next_due_date()` (calendar months and years; the 31st clamps to a shorter month's end). Reopening a job or deleting its open job doesn't touch the schedule yet.
  - Each schedule is locked (`FOR UPDATE SKIP LOCKED`), rechecked and committed on its own. A failure is rolled back and logged, the rest carry on, and the command exits non-zero at the end. `JobForm` deliberately has no job schedule field, so don't add one.
- `Supplier` has an optional `email` (blank stored as NULL, validated by `Email()` on `SupplierForm`), on the form, the overview (as a `mailto:` link), the data export and the suppliers import (an optional `email` column, validated and lowercased like the people import's), not on the index or downloads.
- `Supplier` has tabs Overview and Files.
- Registration, OTP validation, sessions, rate limiting, suspension and `/admin` work. Still missing:
  - `organisation.manage` covers My Organisation (view, edit name, address and telephone, delete); there are no other organisation settings yet
  - record-level rules, for example engineers only seeing jobs assigned to them
- Files: expired files aren't flagged anywhere but their lists.
- No automated tests.
