# flask-play

A facilities management (CAFM-style) SaaS app, pre-production. It tracks sites, assets, jobs (reactive work), job schedules (planned/recurring maintenance) and suppliers.

**Current priority: build out features first. Design and UI polish come later.** Don't restyle or refactor templates unless asked. See "Deferred: design" below.

## Stack

- Flask 3, Flask-SQLAlchemy, Flask-Migrate (Alembic), Flask-WTF (CSRF is on globally), `email-validator` (for WTForms `Email()`), `resend` (email), `reportlab` (PDF downloads), `boto3` (file storage in DigitalOcean Spaces), `tzdata` (UK time zone on Windows), `psycopg[binary]` (SQLAlchemy 2.1 uses psycopg 3 for `postgresql://` URLs) and `gunicorn` (production). They're pinned in `requirements.txt` (direct dependencies only); add new packages there.
- PostgreSQL. Primary keys are UUIDs (`sqlalchemy.dialects.postgresql.UUID(as_uuid=True)`)
- Server-rendered Jinja templates with Bootstrap 5.3 and Bootstrap Icons 1.11.3 (`<i class="bi bi-...">`) from the CDN with SRI hashes, Tom Select 2.4.3 (CDN, SRI, `tom-select.bootstrap5` theme) for searchable selects, plus a small `app/static/js/app.js` (toast auto-hide, Tom Select setup, the person form's group toggle, location narrowing, table Columns menus)
- Windows dev machine, venv at `venv/`, run with `venv/Scripts/python.exe`
- Git repo, `main` pushed to https://github.com/wh80/myfmhub-app. `.gitignore` excludes `.env`, `venv/`, `__pycache__/` and local `*.db` files. Never commit `.env` or secrets.

## Running

```
venv/Scripts/python.exe run.py               # dev server (debug)
flask db migrate / flask db upgrade          # migrations
venv/Scripts/python.exe seeder.py            # add 50 of each record type
venv/Scripts/python.exe seeder.py --clear    # wipe data first; --count N to change amount
flask make-platform-admin <email>            # grant /admin access, creating the user if new (--remove to take it away)
flask create-jobs-for-job-schedules          # raise jobs from due job schedules (run daily by cron)
```

Config comes from `.env` via `config.py` (all of these are loaded into `Config`): `DATABASE_URL`, `SECRET_KEY`, `OTP_PEPPER`, `DO_SPACES_ENDPOINT`/`KEY`/`SECRET`/`BUCKET`, `LOCAL_FILE_FOLDER` (default `instance/files`, gitignored; used when no bucket is set), `RESEND_API_KEY`, `EMAIL_FROM`, `SUPPORT_EMAIL` (default support@myfmhub.com: shown to customers, and where new support ticket notifications go). `MAX_CONTENT_LENGTH` is 25 MB for every request (a 413 redirects back with a message); uploads are limited to 20 MB and imports to 5 MB on top of that. Never hard-code secrets in `config.py`. `SECRET_KEY` and `OTP_PEPPER` are read with `os.environ[...]` and have no fallback, so the app won't start without them; keep it that way.

In local dev, `RESEND_API_KEY` is commented out in `.env`, so sign-in emails, codes included, are printed to the dev server console. That's how you sign in as seeded `@example.com` users. Uncomment it to send real email.

## Data model (`app/models.py`)

- Multi-tenant. `Organisation` is the tenant: `name`, `suspended_at` (set by a platform admin so nobody can sign in to it), `verified_at` (see registration), and `terms_accepted_at` / `terms_accepted_by` (the registrant's person, ondelete SET NULL; `use_alter` with a name and `post_update`, because person refers back to organisation, so `Organisation.people` needs `foreign_keys='Person.organisation_id'`), set by registration and by the seeder (its admin). Every other model except `User`, `OTP` and `UserSession` (the login side, which spans organisations) has a non-null `organisation_id`, and `Organisation` has a `cascade='delete'` relationship to each. Link tables carry no organisation.
- **Users and people** (decided October 2026): `User` is the login, one per email across every organisation. `Person` is someone in one organisation, and their membership of it. One user can have a person in several organisations (`user.people`), for example a contractor who works for two customers, and each organisation controls its own person's name, user group and `can_login`. The app never edits a user from inside an organisation, so one organisation can't affect someone's access to another.
- `User`:
  - unique `email`. The unique constraint is case-sensitive, so lowercase emails before saving or looking them up. There's no password: login is passwordless (OTP).
  - `email_verified_at`, set by the first successful OTP
  - `is_platform_admin`: MyFmHub staff access to `/admin`. It's only set with the CLI command, which creates the user if the email is new. A platform admin can have no people at all; anyone else always has at least one (deleting someone's last person deletes their user, see `services/people.py`).
  - `last_organisation_id` (ondelete SET NULL): the organisation they last worked in, pre-selected on the Select organisation page at their next sign-in.
  - `user.signin_people(otp=None)` lists the people they can sign in as, sorted by organisation name, using `person.can_sign_in()`.
- `Person`: `first_name`, `last_name`, `email`, optional `job_title` and `mobile`, plus:
  - `user_id` (required, ondelete CASCADE), with `UniqueConstraint('organisation_id', 'user_id')`: a user is in an organisation at most once.
  - `can_login` (default False): the organisation's choice. Registration sets it to True.
  - `user_group_id` (ondelete RESTRICT): their permission group in this organisation, see `UserGroup`. Only required when `can_login` is on (`PersonForm.validate_user_group_id`). `person.is_org_admin` is True when it's the Admin group.
  - `person.can_sign_in(otp=None)`: `can_login`, the organisation isn't suspended, and it's verified (or `otp` is the code sent when this person registered it).
  - `Person.email` always equals `person.user.email`. Changing a person's email moves them to the user with that email (`change_person_email()`), never edits the shared user.
- `UserGroup` belongs to an `Organisation` (`organisation.user_groups`, cascade delete) and has `people`. It stores `name` (unique per organisation) and `is_admin`.
  - `UserGroupPermission` rows (`user_group_id` and `permission`, composite PK, no id or timestamps, like a link table) are the permissions it's granted. `user_group.permission_keys` returns them as a set.
  - Registration calls `create_default_groups(org)`, which makes Admin (`is_admin`, full access, can't be renamed, changed or deleted) and Team (every grid permission). The registrant goes in Admin. The seeder does the same: first person Admin, the rest Team.
- `OTP` belongs to a `User` (ondelete CASCADE, `user.otps`). `person_id` (ondelete SET NULL) is set on codes sent for one organisation (registration and invites): signing in with that code goes there, and a registration code is what verifies a new organisation. It stores `code_hash`, an HMAC-SHA256 of the 6-digit code peppered with `OTP_PEPPER`, never the code itself. It also has `expires_at` and `used_at` (both `DateTime(timezone=True)`, unlike the naive `created_at`/`updated_at`; SQLite returns them naive) and `attempts`.
- `UserSession` belongs to a `User` (ondelete CASCADE, `user.sessions`). It stores:
  - `person_id` (ondelete SET NULL): the organisation the session is working in, as the user's person there. Everything organisation-scoped goes through it (`g.person`). NULL while a user with several organisations chooses one, or for a platform admin outside any organisation.
  - `token_hash`: SHA-256 of the cookie token, unique
  - `expires_at`: 30 days
  - `revoked_at`: set it to log a session out
  - `last_seen_at`: written at most every 5 minutes
  - `user_agent` and `ip_address`: `request.remote_addr`. Behind a proxy or load balancer, this needs Werkzeug's `ProxyFix`. It's named `UserSession` to avoid a clash with Flask's `session` and `db.session`.
- `Site` has many `Job`, `Asset`, `JobSchedule` and `Building`, with cascade delete. Optional `main_contact_id` (a person in the organisation, ondelete SET NULL; `site.main_contact`, `person.main_contact_sites`) is a searchable select on the site form (`set_main_contact_choices()` in `routes/sites.py`, everyone in the organisation) and shows on the overview, linked to the person with `people.view`. It's in the data export, not on the index, downloads or import. `Site.name` is unique per organisation (`UniqueConstraint` with `organisation_id`; the site form and the sites import also check case-insensitively).
- **Locations**: `Building` (`name`, `site_id`) belongs to a site and has many `Zone` (`name`, `building_id` ondelete CASCADE), cascade delete. Building names are unique within the site and zone names within the building (DB `UniqueConstraint` plus case-insensitive `name_taken()` checks in the routes and imports). A building's site and a zone's building are set at creation and never change, so records in them can't drift to another site.
  - `Asset`, `Job` and `JobSchedule` have a required `site_id` plus optional `building_id` and `zone_id` (both ondelete SET NULL): deleting a building deletes its zones and leaves its records at the site with no building or zone. The building is always at the record's site and the zone in the record's building. `raise_job()` copies both from the schedule.
- `Job` belongs to a `Site`, and optionally to a `JobSchedule` (`job_schedule_id`, ondelete RESTRICT). Optional `estimated_cost` and `actual_cost` (`Numeric(12, 2)` pounds, on `JobForm` with a £ prefix via `money_field()` from `_number_fields.html`) show on the overview, the data export and nowhere else (not on tables or index downloads).
  - `status` is a key from `JOB_STATUSES` in `app/models.py` (`new`, `open`, `closed`; default `new`, enforced by the `ck_job_status` check constraint). `job.status_label` gives the display text and `jobs/_status_badge.html` renders it as a badge. It's set by the app only, never on `JobForm`.
  - `source` is a key from `JOB_SOURCES` (`planned`, `reactive`, `remedial`; `ck_job_source` check constraint), shown with `job.source_label`. It's required with no default at any level, so every code path that creates a job must set it: the create route sets `reactive`, and raising a job from a schedule should set `planned`. Not on `JobForm`.
  - `closed_at` (Date, nullable) is set only by closing: the job header's Close button (shown with `jobs.close` while the job isn't closed) links to GET `/jobs/<id>/close` (`jobs.close`, needs `jobs.close`). The page has a `JobCloseForm` defaulting to the UK date (`uk_today`), which can't be in the future or before `job.raised_on` (the UK date of `created_at`, via `uk_date()` in `services/scheduling.py`); this applies to every job, and Update schedule re-checks it. POST sets status `closed` and `closed_at` and redirects to the job. For a job where `job.closes_with_schedule_update` is True, it saves nothing and redirects to Update schedule below with `?closed_at=`. The close page reads `?closed_at=` too, so Update schedule's Back button keeps the chosen date. An already-closed job redirects back with a warning. A closed job shows a Reopen button instead: a POST form to `/jobs/<id>/reopen` (`jobs.reopen`, needs `jobs.reopen`, POST only) that sets status `open` and clears `closed_at`.
  - **Sequence rules for planned jobs** (each close date sets the schedule's next due date, so these keep a schedule to one open job in order; the support guide explains them to customers):
    - a closed planned job can't be reopened (route refuses, Reopen button hidden)
    - an open planned job can't be deleted (GET and POST refuse, Delete button disabled); a closed one can
    - a planned job's `due` can't be edited: the edit page shows it read-only and the route ignores the field
    - a job schedule that has raised any jobs can't be deleted (GET and POST refuse, Delete button disabled). Deleting a site still cascades through its schedules and jobs.
    - backstop: the partial unique index `uq_job_open_per_schedule` on `job (job_schedule_id) WHERE status != 'closed'` (in `Job.__table_args__`) means the database refuses a second open job on a schedule, whatever the app does. A breach raises `IntegrityError`; in the daily run it's rolled back and logged like any other failure. The seeder keeps to it too: a schedule gets at most one open job, and that schedule's `next_job_creation_date` is NULL, as after `raise_job()`.
  - **Update schedule** (GET/POST `/jobs/<id>/update-schedule?closed_at=<yyyy-mm-dd>`, `jobs.update_schedule`, needs `jobs.close` rather than `job_schedules.edit`, because it's part of closing) is the second step of closing a planned job. `job.closes_with_schedule_update` is True for a planned job whose schedule's `next_job_creation_date` is NULL, meaning `raise_job()` is waiting on it. The page shows the schedule (description, frequency, site) and offers `next_due_date(closed_at, frequency)` as the next due date. `JobScheduleNextDueForm` refuses a date before today or after that calculated date (or after today, when the calculated date has already passed). POST closes the job (status and `closed_at`) and sets the schedule's `next_due` and `next_job_creation_date` in one commit, so a job is never closed with its schedule left waiting. There's no skip: leaving the page leaves the job open. A closed job, or one that doesn't close with a schedule update, redirects to the job with a warning, and a missing or future `closed_at` redirects to the close page.
- `JobSchedule` belongs to a `Site` and has many `jobs`. Optional `estimated_cost` (pounds) and `estimated_duration` (`Numeric(6, 2)` days, so 0.5 is half a day; `number_field()` with step 0.25, shown with the `days` filter) are on the form, overview, data export and the job schedules import (`money` and `days` column kinds), not on tables. Copy copies both, and `raise_job()` copies `estimated_cost` to the job. `next_due`, `frequency` (a key from `FREQUENCIES` in `app/services/scheduling.py`; `job_schedule.frequency_label` gives the display text) and `notice_days` (0–365, and no more than the frequency's shortest gap in `FREQUENCY_MIN_DAYS`, checked by `JobScheduleForm.validate_notice_days`) are required. The view header's Copy button (shown with `job_schedules.create`) links to `/job-schedules/create?copy_from=<id>`: GET pre-fills description, work required, frequency, notice days, statutory compliance and active from that schedule (`org_get_or_404`). Next due (deliberately: it should be chosen, not carried over), site, building, zone and linked assets aren't copied, and the new schedule keeps no link to the original. After create, a user with `job_schedules.edit` goes to `/job-schedules/<id>/created` (`job_schedules.created`, needs view), which says it's saved and asks whether to add assets now: Yes goes to `link_assets`, No to the index. Without edit, create flashes and goes straight to the index. `next_job_creation_date` is never on a form: create and edit set it with `job_creation_date(next_due, notice_days)`. It can be in the past when the due date is close. It's NULL once a job has been raised for `next_due` (see `raise_job()`). `is_active` (default True, on the form as "Active") turns the schedule off: `due_job_schedules()` skips inactive schedules, so they raise no jobs. `check_reactivation()` in `routes/job_schedules.py` makes an edit that turns it from inactive to active have a `next_due` after today. The job schedules import has an optional `active` Yes/No column (`Column(..., blank_means_yes=True)`), so a blank cell or a file without the column imports active schedules. Reactivation's future-date rule doesn't apply to imports, which only create. `job_schedule.next_job_creation_label` is how pages and the index download show Next Job Creation: "Inactive", "Pending current job closure" (NULL) or the date. `job_schedule.open_job` is the schedule's job that isn't closed, or None. Edit (GET and POST) redirects to the view with a warning while there is one, so a schedule never has two open jobs; the header's Edit button is disabled and the overview shows an alert linking to the job and to the support guide. Because of that, edit always recalculates `next_job_creation_date`, which also restarts a schedule whose open job was deleted.
- `Asset` belongs to a `Site`. `asset_number` and `serial_number` are optional (blank stored as NULL) and each unique per organisation: there's a DB `UniqueConstraint` with `organisation_id`, and `check_unique()` in `routes/assets.py` checks case-insensitively and adds form errors. It links many-to-many to jobs (`job_assets` table) and to job schedules (`job_schedule_assets` table). The link FKs use ondelete CASCADE, so deleting a record removes only its link rows. `assigned_to_id` (ondelete SET NULL) is the person it's assigned to (`asset.assigned_to`, `person.assigned_assets`), set only on the Assign page: the view header's Assign button (with `assets.edit`) goes to GET/POST `/assets/<id>/assign` (`assets.assign`, needs `assets.edit`), a select of every person in the organisation plus Unassigned (`AssetAssignForm`, so WTForms refuses anyone else). The overview shows Assigned To, linked to the person with `people.view`. It's in the assets data export, not on `AssetForm`, the index or the import. `parent_id` (self-referencing, ondelete SET NULL; `asset.parent`, `asset.sub_assets` by description) makes it a sub-asset. It's only set at creation from the parent's Sub-Assets tab (`assets.sub_assets`, `/assets/<id>/sub-assets`, needs view): its Create Sub-Asset button (with `assets.create`) goes to `/assets/create?parent_id=<id>` (`org_get_or_404`, so another organisation's asset is a 404), which pre-fills the parent's site, building and zone (changeable) and redirects back to the tab. The parent never changes, so there are no loops; sub-assets can have sub-assets. The regular create form and `AssetForm` have no parent field. Deleting a parent makes its sub-assets top-level (the delete page warns). The overview shows Part Of, and the export has Part Of Asset ID. The index and import don't show or set it.
- `ImportEvent` records one CSV import. It stores `import_type` (a key from `IMPORT_TYPES`), `filename`, `rows_imported`, `errors` (JSON `[{'row', 'error'}]`, with the header as row 1), the organisation, `person_id` (who imported it), and `undone_at`/`undone_by_id`. Both are person FKs, ondelete SET NULL, and the relationships need `foreign_keys`. Person also has `import_event_id`, so these two FKs are `use_alter=True` with names, and the migration adds them with `batch_op.create_foreign_key` after both tables exist (Alembic leaves `use_alter` FKs out of `create_table`). `Site`, `Asset`, `JobSchedule`, `Supplier` and `Person` have a nullable `import_event_id` (ondelete SET NULL) set on imported records.
- `File` (`organisation.files`, cascade delete): `description` (required), optional `expires` (`file.is_expired` against the UK date), `size_mb` (Numeric, summed for Storage Used), `filename` (as uploaded, for downloads), `content_type` (from the extension via `FILE_TYPES`, never from the browser) and `storage_key` (unique, `<organisation id>/<file id>.<ext>`). Only `description`, `expires` and `file_category_id` can be edited (`files.edit`); the stored file, `filename`, `content_type`, `size_mb` and `storage_key` never change, so replacing a file means uploading a new one. Link tables `site_files`, `building_files`, `zone_files`, `job_files`, `asset_files`, `job_schedule_files`, `person_files` and `supplier_files` (both FKs ondelete CASCADE) give `file.sites`... and `<record>.files` (by description). Deleting a record only removes its link rows; deleting a file (`delete_files()`) removes it from storage too.
- **Reference data** (categories and conditions): `JobCategory`, `AssetCategory`, `AssetCondition`, `BuildingCondition`, `SupplierCategory` and `FileCategory` share the `ReferenceItem` mixin in `models.py`: `description` (100 chars, unique per organisation by `UniqueConstraint` plus case-insensitive `find_item()` checks) and `organisation_id` (cascade delete from `Organisation`; they're in `DELETE_ITEMS`). `str(item)` is its description, so templates show `{{ asset.asset_category or '-' }}`.
  - Records point at them with optional FKs (ondelete SET NULL) and a relationship of the same name: `Job.job_category`, `JobSchedule.job_category`, `Asset.asset_category`, `Asset.asset_condition`, `Building.building_condition`, `Supplier.supplier_category` and `File.file_category` (on upload and file edit).
  - `Asset` and `Building` have `condition_set` (Date), set by the app only: `set_condition(record, column, condition_id)` (`services/reference_data.py`) sets it to `uk_today()` when the condition changes on create or edit, clears it when the condition is cleared, and leaves it otherwise. It's shown on overviews, never on a form.
  - `raise_job()` copies the schedule's job category to the job, and Copy (`?copy_from=`) pre-fills it.
- **Support tickets**: `SupportTicket` (`description` Text, `status` a `SUPPORT_TICKET_STATUSES` key, `open`/`closed` with the `ck_support_ticket_status` check, set by the app only; `ticket.status_label`) belongs to an organisation (cascade delete, deliberately not in `DELETE_ITEMS`: they're the platform's records, so they go with the organisation without a box to tick) and has `created_by` (a person, ondelete SET NULL, `person.support_tickets`, so deleting the person keeps the ticket). `SupportTicketNote` (`description`, `created_by` a `User`, ondelete SET NULL) belongs to the ticket (`ticket.notes`, oldest first, cascade delete); like `UserGroupPermission` it has no `organisation_id` of its own.
- Every model has `id`, `created_at` and `updated_at`.
- History: these were renamed from WorkOrder → Job, PPMSchedule → JobSchedule, Contractor → Supplier. Old names should not appear anywhere.
- Migrations: a regenerated initial migration (currently `3965cc9e40a2_initial.py`, plus the stacked `b4e7d2c91f35_add_job_costs.py`, `c8a1f6e3d920_add_support_tickets.py` and `d2b5e8f04a17_add_site_main_contact.py`, hand-written because the initial one was already pushed; generated by Alembic with LF line endings, which is fine). It's pre-production, so the user usually deletes and regenerates migrations rather than stacking them (on 2026-10-28 they briefly stacked one before regenerating again). **After regenerating, re-add the `use_alter` foreign keys by hand**: autogenerate writes them inside `create_table`, where Postgres silently leaves them out (SQLite keeps them, so scratch tests don't notice). Remove them from `create_table` and add `fk_organisation_terms_accepted_by_id`, `fk_import_event_person_id` and `fk_import_event_undone_by_id` with `batch_op.create_foreign_key` straight after `person` is created, and drop them in `downgrade()` before `person`. Check with `DATABASE_URL=postgresql://x:y@localhost/z flask db upgrade --sql | grep "ADD CONSTRAINT fk_"`, which needs no database.

## Code layout and conventions

- Routes: one blueprint per resource in `app/routes/`: `sites`, `assets`, `jobs`, `job_schedules` (URL `/job-schedules`), `suppliers`, `people`, `user_groups` (URL `/user-groups`), `buildings`, `zones`, plus `my_organisation` (URL `/my-organisation`) and `files`. All are registered in `app/__init__.py`. URLs use hyphens; endpoints and templates use underscores.
- `organisations` blueprint (`/organisations` prefix) holds `register()`, but that view is mounted at the root `/register` (`/login` is mounted the same way, see `auth` below) with `app.add_url_rule(..., endpoint='organisations.register')` in `create_app`, so `url_for('organisations.register')` gives `/register`. `terms()` (`organisations/terms.html`, a placeholder for now) is mounted the same way at the public `/terms`, and `RegisterForm.accept_terms` is a required checkbox linking to it (registration records it in `terms_accepted_at` and `terms_accepted_by`). Registration creates an Organisation and an admin Person (with `can_login`) in one commit. The email is stripped and lowercased; an email that already has a user reuses it (`find_or_create_user()`), so one login can register several organisations, after a rate-limit check on that user. The organisation starts with `verified_at` NULL: anyone can type any email here, so it isn't offered at sign-in or in Switch organisation until the code sent now (`create_otp(user, person)`, which carries the person) is entered, and `choose_person()` then sets `verified_at`. It redirects to the validate page. If sending fails it still goes there, with a warning to use "Send a new code", which keeps the organisation.
- **People** (`/people`, `app/routes/people.py`):
  - Index, view, create, edit and delete like the other resources, gated by the `people.*` permissions like everything else.
  - The form has a required User Group select, built from `org_query(UserGroup)`. Non-admins don't see the Admin group in the list, can't edit, delete or resend to an admin (`require_can_manage`, 403), and can't change their own group.
  - The organisation must always have at least one admin who can log in (`other_active_admins(person)`). Edit refuses to move the last one out of Admin or turn off their login, and delete refuses to remove them.
  - After an edit, if you can no longer see people (you moved yourself to a smaller group), you're sent to the dashboard.
  - Templates: tabbed `people/view/` (Overview, and Assets: the person's `assigned_assets` through `asset_list.html`; the Assets tab and `people.assets` also need `assets.view`, so the tab is hidden and the route gives a 403 without it) and an inline table in `index.html`. The search covers first, last and full name, email and job title.
  - Create lowercases the email. `email_in_organisation()` refuses an email already used by someone in this organisation. Other organisations don't matter: an email with a user elsewhere links to that user (`find_or_create_user()`), with the same response as a new one, so the form never reveals that an email has an account.
  - Edit: changing the email calls `change_person_email()` (`services/people.py`), which moves the person to the user with the new email (creating it), ends the person's sessions here, and deletes the old user if nothing else uses it. It never edits a user's email, because the user may be in other organisations (otherwise one organisation could change Bob's email to its own address and sign in as Bob elsewhere). Changing your own email signs you out.
  - Turning `can_login` on, or changing the email of someone who can log in, calls `send_invite()`: it checks the rate limit, then `create_and_send_otp(person.user, person, invited_by=<name>)`, whose subject is "<name> added you to <organisation> on MyFmHub", and flashes the outcome. Adding someone without login sends nothing. Turning login off calls `revoke_person_sessions(person)`, which ends only the sessions working in this organisation.
  - POST `/people/<id>/send-invite` (needs `people.edit`) is the "Resend sign-in email" button on the view page. It shows when `can_login` is on and it isn't your own record, and it calls `send_invite()`.
  - Delete calls `delete_person()`: it ends the person's sessions here, deletes the person, and deletes their user only if this was their last person (and they aren't a platform admin).
  - Nobody can remove their own `can_login` or delete themselves.
- **Permissions** (`app/services/permissions.py`):
  - Keys are `<resource>.<action>`. `RESOURCES` (sites, buildings, zones, assets, jobs, job_schedules, suppliers, people, files) × `ACTIONS` (view, create, edit, delete), less `NOT_GRANTABLE` (grid cells shown as n/a; empty at the moment), plus `EXTRA_PERMISSIONS` (`jobs.close`, `jobs.reopen`, `imports.manage`, `exports.manage`, `reference_data.manage`, listed under the grid), make up `GRANTABLE`, the grid on the user group pages.
  - `ADMIN_ONLY` (`organisation.manage`, `sessions.manage`, `user_groups.manage`) is never stored on a group: only the Admin group has these.
  - `can(person, key)`, called with `g.person`: the Admin group always passes, otherwise the key must be in the person's group's `permission_keys`. Templates use the global `can('jobs.edit')` (the signed-in user in the session's organisation) to hide buttons and navbar links.
  - `clean_permissions()` drops unknown and admin-only keys, and adds `<resource>.view` whenever create, edit or delete is given. `set_permissions(group, keys)` applies the difference.

People routes and import undo use them; don't delete or re-point a person's user any other way. Resource CRUD stays in the routes.
  - `services/email.py`: `send_email(to, subject, html)` sends through Resend. If `RESEND_API_KEY` is empty, it logs the email (code included) instead, which is useful in dev and tests.
  - `services/auth.py`: `create_otp(user, person=None)` expires the user's unused OTPs (it doesn't delete them, so the rate limit can count them, and rows older than a day are deleted), saves a new one (expires in 15 minutes, `person` is the organisation it's for) and returns `(otp, code)`. `send_otp_email(otp, code, welcome=False, invited_by=None)` emails `templates/emails/auth/send_otp.html` with the code and a link to `/auth/validate/<otp_id>`. `create_and_send_otp(user, person=None, ...)` does both and returns the OTP. `welcome=True` (registration) and `invited_by="Name"` (people) change the subject and opening line. Every code email links to `/login` for a fresh code. Also in `services/auth.py`:
    - `check_otp_rate_limit(user)` returns an error message or None: one code per 60 seconds and 5 per hour, per user, counted from OTP rows in the database. `/login`, resend, invites and registration with an existing email call it.
    - `signin_refusal(user, otp=None)` returns None if the user can sign in (a platform admin, or `user.signin_people(otp)` isn't empty), otherwise `ORGANISATION_SUSPENDED_MESSAGE` (every organisation that would let them in is suspended) or `NO_LOGIN_MESSAGE`.
    - `verify_otp(otp, code)` returns an error message, or None on success. It checks `signin_refusal(otp.user, otp)`, and refuses codes that are already used, expired or locked (5 wrong attempts) and counts wrong attempts. On success it sets `used_at` and `email_verified_at`.
    - `choose_person(user, otp=None)` picks the organisation a new session starts in: the code's person (registration or invite), else their only one, else None, so someone in several organisations always selects one at a fresh sign-in. It verifies an organisation registered with the code and sets `last_organisation_id`. `switch_person(user_session, person)` moves a session.
    - `create_session(user, person=None)` saves a `UserSession` and returns the raw token. `set_session_cookie(response, token)` sets the `auth_session` cookie (HttpOnly, SameSite=Lax, 30 days, Secure unless `AUTH_COOKIE_SECURE=false`).
    - `get_active_session(token)` returns the `UserSession`, or None if it's revoked or expired, or `signin_refusal()` refuses the user. If the session's person can't sign in any more, it clears the session's person (a backstop; revoking normally handles it). It touches `last_seen_at`.
    - `active_sessions()` is a query for sessions that aren't revoked or expired. `active_session_counts(users)` returns `{user_id: count}`.
    - Revoking: `revoke_session(user_session)`, `revoke_person_sessions(person)` (sessions working in that person's organisation), `revoke_user_sessions(user)` (everywhere, /admin only), `revoke_organisation_sessions(org)` (sessions working in it) and `revoke_all_sessions()`.
    - `suspend_organisation(org)` sets `suspended_at` and revokes the sessions working in it; its people's other organisations aren't affected. `reinstate_organisation(org)` clears it.
    - `clear_session_cookie(response)` deletes the cookie. `as_utc()` normalises SQLite's naive datetimes for comparison.
- `auth` blueprint (`/auth`):
  - Its `before_app_request` sets `g.user_session`, `g.user`, `g.person` (the session's person, None until an organisation is chosen) and `g.organisation` from the `auth_session` cookie on every request (all None when signed out).
  - `login()` is mounted at the root `/login` (endpoint `auth.login`) in `create_app`. It sends a code to an existing user and redirects to validate. An unknown email gets a form error, which reveals whether an account exists, as registration already does. A signed-in user is redirected to the dashboard.
  - `login` refuses users `signin_refusal()` refuses, then checks the rate limit before sending.
  - A user whose only way in is through suspended organisations gets `auth/organisation_suspended.html` (403) from `organisation_suspended()`, both at `login` and when opening `validate`. It tells them to contact their system admin or `SUPPORT_EMAIL`.
  - `logout` (POST `/auth/logout` only, CSRF-protected) revokes `g.user_session`, clears the cookie and redirects to `/login`.
  - `resend` (POST `/auth/validate/<otp id>/resend`) is the "Send a new code" button on the validate page. It's for an email that never arrived or a code that's expired, used or locked. It sends a new code to the same user for the same person (rate-limited, keeps `?next`), so a registration or invite code still goes to its organisation, then redirects to the new code's validate page. It refuses users `signin_refusal()` refuses.
  - An unknown OTP id (codes are deleted after a day, so old email links hit this) on `validate` or `resend` goes to `expired_link()`, which redirects to `/login` with a message instead of a 404.
  - `validate` (GET/POST `/auth/validate/<otp id>`): on a correct code it calls `choose_person()`, creates a session in that organisation, sets the cookie and redirects to `next` or the dashboard. With no person chosen it goes to Switch organisation (several organisations) or `/admin` (a platform admin with none). On a wrong code it re-renders with the error on the code field.
  - **Switch organisation** (GET/POST `/auth/organisation`, `auth.switch_organisation`, `user_required` so it works before one is chosen): a select of `g.user.signin_people()` by organisation name (`SwitchOrganisationForm`; WTForms refuses anyone else's person). With no organisation chosen yet (a fresh sign-in) it's titled Select organisation and pre-selects `last_organisation_id`. POST calls `switch_person()` and goes to the dashboard, since records belong to one organisation (or to `next` when none was chosen yet). The navbar dropdown links to it when there's another organisation to go to.
  - `/auth/sessions` (login required, links from the navbar dropdown), with an Organisation column:
    - Admins (`sessions.manage`) see "Sessions": every active session working in their organisation plus their own, with Revoke. Sessions of the same people working in other organisations are hidden (their device and IP are none of this organisation's business).
    - Everyone else sees "Your sessions": their own, in any organisation.
    - POST route: `/auth/sessions/<id>/revoke` (404 outside your scope).
    - There's deliberately no suspend here. An organisation removes someone's access by turning off `can_login` on their person record, and revoking is for signing a single device out, for example a compromised one.
- `admin` blueprint (`/admin`, platform admins only):
  - `before_request(require_platform_admin)` gives a 404 to signed-in non-admins and redirects signed-out visitors to login.
  - Tabs (`admin/_tabs.html`): Organisations (the `/admin/` index), Sessions, Users and Support Tickets. All are paginated. Sessions and Users share `admin/_filters.html` (email search and an organisation filter).
  - Organisations: name search, people and active session counts, an Unverified badge, a Sessions link, and Suspend or Reinstate (POST `/admin/organisations/<id>/suspend|reinstate`). You can't suspend the organisation your session is working in.
  - Sessions: revoke one, "Revoke all sessions for <org>" (when filtered; POST `/admin/organisations/<id>/revoke-sessions`) and "Revoke all sessions everywhere" (POST `/admin/sessions/revoke-all`), to force everyone to sign in again after a compromise.
  - Users: one row per login, with its organisations (the organisation filter matches any of them), a Platform admin badge, and "Revoke sessions" (POST `/admin/users/<id>/revoke-sessions`, every organisation).
  - People are never suspended individually. Per-person actions are session revokes only, and access is controlled by `can_login`, which the organisation owns.
- Session actions live in `app/routes/helpers.py`: `revoke_and_redirect` (one session) and `signed_out_or_back(message, fallback)` (after a bulk revoke: it signs you out if your own session went, otherwise goes back), plus `back_to`.
  - Forms post a hidden `next` (`request.full_path`) so the redirect keeps filters and page. It's checked with `safe_next_url`.
  - Revoking your own current session (including revoke-all on your own organisation) signs you out.
  - Partials: `auth/session_list.html` (both areas) and `auth/user_list.html` (`/admin/users`), configured with variables set before the include: `revoke_endpoint`, `revoke_user_endpoint` and `show_organisation`.
- Jinja filters (registered in `create_app`): `datetime` formats a datetime as `21-10-2026 14:05`, `date` formats a date as `21-10-2026`, `currency` formats a number as `£12,345.60` (money is stored as `Numeric(12, 2)` pounds), and `days` formats a duration as `0.5 days` or `1 day`. All give `-` for None. Times are UTC.
- `parse_uuid(value)` in helpers returns a UUID or None, for ids in query strings. Unlike a raw string, it works on SQLite too.
- `require_login()` / `login_required` (in `app/routes/helpers.py`) redirect to `/login`. GET requests add `?next=<full path>`. POSTs don't, and nothing is changed. They also need `g.person`: a signed-in user with no organisation chosen goes to Switch organisation (with `next`), and a platform admin with none to `/admin`. `require_user()` / `user_required` only need a signed-in user (Switch organisation; `require_platform_admin` uses it too).
  - `login` passes `next` on to the validate URL, and `validate` redirects to it after a correct code, falling back to the dashboard.
  - `next` is always checked with `safe_next_url()`, which allows only local paths (no `//`, backslashes or other hosts).
  - The validate link in emails has no `next`.
  - The dashboard uses the decorator. Resource blueprints use the hook.
- Navbar: when signed in, a `bi-person-circle` icon opens a dropdown with the name, email, current organisation, Switch organisation (when there's another), and a Sign out button (a POST form). When signed out, it shows a Sign in link.
- `dashboard` blueprint: `/dashboard/` renders `dashboard/index.html`. It's the landing page after login.
  - With `jobs.view`, it shows four job cards: Compliance Status (green tick, or red with the number of overdue statutory jobs), Compliance Risks (statutory, not closed, due today to 7 days ahead), Overdue Jobs and New Jobs.
  - Each card links to `/jobs` with filters that give the same count, so keep the dashboard queries and the `jobs.index` filters in step. Overdue is `overdue_conditions(uk_today())` in `services/jobs.py`, used by both. The jobs Status filter has a filter-only `not_closed` option. `/` (endpoint `dashboard.root`, mounted in `create_app` like `/register` and `/login`) redirects to it.
- People who can log in need a group: call `create_default_groups(org)` and pass `user_group=admin` or `team` (and `can_login=True`, and a `user`) when creating a `Person` directly, and post `user_group_id` in person forms. A seeded or test organisation needs `verified_at` set, or nobody can sign in to it.
- Testing signed-in routes: create a session with `create_session(user, person)` inside `app.test_request_context()`, then `client.set_cookie('auth_session', token, domain='localhost')`. Or sign in for real: patch `app.services.auth.send_email` to capture the code, and patch `check_otp_rate_limit` in the route modules that import it, or repeat sign-ins within a minute are refused. Test emails need a real-looking domain such as example.com: `email-validator` rejects `.test`.
- Testing auth with `app.test_client()`: the auth cookie is Secure, so pass `base_url='https://localhost'` on requests. Flask's own `session` cookie (flash messages, CSRF) is set too, so look for `auth_session` specifically.
- Email templates live in `templates/emails/<area>/` as standalone HTML with inline styles (they don't extend `base.html`).

## Testing

There's no test suite yet. Changes have been checked with throwaway scripts against SQLite, never the dev Postgres database:
- Set `DATABASE_URL=sqlite:///<scratch path>/x.db`. An environment variable overrides `.env`.
- Run `db.create_all()`, then `seeder.py`, then use `app.test_client()` with `WTF_CSRF_ENABLED = False`.
- Postgres UUID columns work on SQLite through SQLAlchemy's generic UUID fallback. One catch: SQLite rejects string IDs assigned to UUID columns (`'str' object has no attribute 'hex'`), for example `site_id=form.site_id.data` in create and edit routes. Postgres accepts them, so treat that error as a test-setup artifact, not an app bug. To test successful form saves anyway, patch the bind processor before `create_app()`: wrap `sqlalchemy.sql.sqltypes.Uuid.bind_processor` so its processor converts a `str` with `uuid.UUID(value)` first.

## Known gaps / feature backlog

- **Files export**: the zip is built by a thread in the web server, in a temporary file, so it uses the web instance's memory, CPU and disk while it runs, and a deploy or restart part-way through fails it (the user asks again). If exports become common or very large, move it to a worker.
- **Raising jobs from schedules**: `flask create-jobs-for-job-schedules` (`app/commands.py`) calls `create_scheduled_jobs()` in `services/jobs.py`. It's meant to run once a day from a DigitalOcean App Platform cron job.
  - It picks schedules with `next_job_creation_date <= uk_today()`. It uses `<=` so a missed run or a creation date already in the past is still caught. NULL never matches, so a schedule has at most one job raised and waiting at a time, and one run raises at most one job per schedule.
  - "Today" is the UK date (`Europe/London` via `zoneinfo`, which needs the `tzdata` package on Windows), never the server's UTC date, so BST doesn't shift which day a schedule falls on.
  - `raise_job()` copies description, work required, statutory compliance, site, building, zone, job category, estimated cost, organisation and linked assets. It sets `due` from `next_due`, `job_schedule_id`, status `new` and source `planned`. It leaves `next_due` unchanged and sets `next_job_creation_date` to NULL. The schedule moves on when the job is closed, through Update schedule (see `Job`), using `next_due_date()` (calendar months and years; the 31st clamps to a shorter month's end). Reopening a job or deleting its open job doesn't touch the schedule yet.
  - Each schedule is locked (`FOR UPDATE SKIP LOCKED`), rechecked and committed on its own. A failure is rolled back and logged, the rest carry on, and the command exits non-zero at the end. `JobForm` deliberately has no job schedule field, so don't add one.
- `Supplier` isn't related to anything except its organisation yet (for example, a supplier assigned to a job). It has no tabs.
- Registration, OTP validation, sessions, rate limiting, suspension and `/admin` work. Still missing:
  - `organisation.manage` covers My Organisation (view and delete), but there's no way to edit the organisation's name or settings yet
  - record-level rules, for example engineers only seeing jobs assigned to them
  - an IP-based limit on `/login` (the per-user limit doesn't stop one client trying many emails), for example Flask-Limiter with Redis
- Organisations registered but never verified (nobody entered the code) are never cleaned up. /admin shows them as Unverified; a periodic delete of old unverified organisations would tidy them.
- Files: there's no file count or size quota per organisation, and expired files aren't flagged anywhere but their lists.
- No automated tests.
